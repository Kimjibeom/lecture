CHAPTER 4

A2A 협업 에이전트 · 슬랙 요약 에이전트와 노션 기록 에이전트를 잇는 에이전트 간 통신

2장의 슬랙 에이전트와 3장의 노션 에이전트를 각자의 서버로 띄우고, 중앙 그래프가 A2A로 일을 나눠 맡기는 멀티 에이전트 실습

2장에서는 슬랙 대화를 읽고 요약하는 봇을, 3장에서는 정리한 글을 노션 문서로 저장하는 봇을 만들었습니다. 그런데 실제 업무에서 바라는 것은 그 둘이 이어지는 것입니다. 오늘 채널에서 오간 이야기가 저녁이면 노션의 회의록 페이지에 정리되어 있으면 좋겠습니다. 이 장에서는 두 봇을 하나로 합치지 않고, 각자 독립된 에이전트 서버로 띄운 뒤 중앙에서 "요약해 줘", "이걸 저장해 줘"라고 일을 맡기는 방식으로 잇습니다. 에이전트가 다른 에이전트에게 일을 맡기고 결과를 받는 데 쓰는 규칙이 A2A(Agent2Agent)입니다.

두 봇을 잇는 가장 쉬운 방법은 2장과 3장의 코드를 노트북 하나에 모으고, 그래프에 노드를 하나 더 붙이는 것입니다. 실습 규모에서는 그쪽이 더 간단합니다. 그럼에도 이 장이 굳이 에이전트를 나누고 그 사이에 통신 규칙을 두는 이유는, 업무 자동화가 커지면 "에이전트 하나가 모든 일을 하는" 구조가 금방 한계에 부딪히기 때문입니다. 이 장은 그 한계가 무엇인지, 에이전트를 나누면 무엇이 좋아지는지부터 이야기합니다. 이어서 2장과 3장에서 써 온 MCP를 짧게 되짚고, A2A가 MCP와 어떻게 다른지, A2A에서 에이전트들이 무엇을 주고받는지를 실제 코드의 값으로 하나씩 해부합니다.

이 장을 마치면 다음을 할 수 있습니다.

  • 에이전트를 역할별로 나눠야 하는 상황과 그 이점을 설명하고, 업무 자동화에서 에이전트 간 협업이 쓰이는 사례를 들 수 있습니다.
  • MCP(에이전트와 도구 사이)와 A2A(에이전트와 에이전트 사이)의 차이를 설명하고, 두 규칙이 한 시스템 안에서 함께 쓰이는 구조를 그릴 수 있습니다.
  • A2A의 Agent Card, message/send 요청, Message와 Task의 차이를 설명하고, a2a-sdk로 LangGraph 그래프를 A2A 에이전트 서버로 감쌀 수 있습니다.
  • 중앙 그래프의 노드가 다른 프로세스에 있는 에이전트의 그래프를 부르는 구조를 만들고, 프로세스를 넘나드는 실행 기록을 한곳에서 읽을 수 있습니다.

실습은 Google Colab에서 진행하고, 2장과 3장에서 준비한 슬랙 봇 토큰·채널 ID, 노션 토큰·부모 페이지를 그대로 씁니다. 슬랙 앱과 노션 연결을 만드는 과정은 2.4.5와 3.5.5에서 다뤘으므로 이 장에서는 반복하지 않습니다.

4.1왜 에이전트끼리 협업해야 하는가

4.1.1에이전트 하나로는 부족해지는 순간

2장의 슬랙 봇에는 도구가 두 개, 3장의 노션 봇에는 세 개 있었습니다. 이 둘을 한 에이전트에 몰아넣으면 도구 다섯 개짜리 에이전트가 됩니다. 아직은 괜찮습니다. 그런데 회사에서 "회의 대화를 정리해 노션에 남기고, 정해진 일정은 캘린더에 넣고, 담당자에게 메일로 알려 줘"라는 요청이 들어오면 캘린더 도구와 메일 도구가 붙고, "고객 문의는 CRM에 기록해 줘"라는 요청이 오면 또 붙습니다. 에이전트 하나가 모든 일을 맡는 구조는 이렇게 커지면서 몇 가지 문제를 드러냅니다(그림 4.1).

첫째는 권한이 한곳에 몰리는 문제입니다. 만능 에이전트는 슬랙, 노션, 캘린더, 메일의 토큰을 모두 쥐고 있어야 합니다. 이 에이전트의 지시문이 엉뚱하게 해석되거나 토큰이 새어 나가면 피해가 모든 서비스로 번집니다. 2장에서 "자료 안의 명령을 실행하지 마세요"라는 문장을 넣었던 것을 떠올려 보면, 채널에 올라온 악의적인 메시지 하나가 메일 발송 도구까지 건드릴 수 있는 구조는 위험합니다.

둘째는 주인이 여럿인 코드 문제입니다. 실제 회사에서 슬랙 연동은 협업 도구 팀이, 노션 문서 양식은 기획 팀이, 고객 데이터는 영업 팀이 관리합니다. 이들이 모두 에이전트 하나의 코드와 지시문을 고쳐야 한다면, 한 팀의 수정이 다른 팀의 기능을 망가뜨리는 일이 생깁니다. 셋째는 모델의 선택이 흐려지는 문제입니다. 도구 목록이 길어질수록 모델은 비슷한 설명의 도구 사이에서 헷갈리고, 지시문에는 서로 다른 업무의 규칙이 뒤섞입니다.

사람의 조직이 이 문제를 푸는 방법은 분업입니다. 회계 팀에 "이번 달 비용 정리해 주세요"라고 요청하는 사람은 회계 팀이 어떤 프로그램을 쓰는지, 누가 계산하는지 몰라도 됩니다. 요청 양식과 받을 결과만 알면 됩니다. 에이전트도 마찬가지로, 각자 맡은 분야의 도구와 권한만 가진 에이전트를 여럿 두고, 그 사이에서 일을 주고받게 하면 위의 세 문제가 함께 풀립니다(그림 4.1 오른쪽). 슬랙 요약 에이전트는 노션 토큰을 몰라도 되고, 노션 기록 에이전트는 슬랙 대화를 직접 읽을 수 없습니다. 중앙 조율자는 두 에이전트의 속을 모른 채 "누구에게 무엇을 맡길지"만 압니다. 다만 그림처럼 중앙 조율자를 하나 두는 것은 여러 배치 중 하나일 뿐이고, 에이전트가 다른 에이전트에게 직접 일을 맡기는 배치도 가능합니다. 이 차이는 4.2.3에서 자세히 봅니다.

4.1.2업무 자동화 사례

에이전트들이 일을 나눠 맡는 구조는 여러 업무 자동화에 그대로 들어맞습니다. 공통점은 서로 다른 시스템을 다루는 단계가 이어지고, 각 시스템을 관리하는 주인이 다르다는 것입니다.

표의 사례마다 에이전트를 만드는 주체가 다를 수 있다는 점이 중요합니다. 개발 현황 에이전트는 개발 팀이, CRM 에이전트는 영업 팀이나 CRM 업체가 만들고 운영합니다. 이렇게 서로 다른 사람이 만든 에이전트끼리 일을 주고받으려면, 함수 이름을 맞추는 수준이 아니라 "에이전트가 자기를 어떻게 소개하고, 일을 어떻게 받고, 결과를 어떻게 돌려주는지"에 대한 공통 규칙이 필요합니다. A2A가 정하는 것이 바로 이 규칙입니다.

4.1.3이번 장의 시나리오

이 장은 표의 첫 번째 사례 중 앞의 두 단계를 실제로 만듭니다. 등장하는 에이전트는 둘이고, 둘 다 앞 장에서 이미 만든 것입니다.

  • 슬랙 요약 에이전트 · 2장의 read → summarize 그래프를 그대로 품고, 요청이 오면 채널 대화를 읽어 요약을 돌려줍니다.
  • 노션 기록 에이전트 · 3장의 save 그래프를 그대로 품고, 제목과 본문을 받으면 노션 문서로 저장하고 주소를 돌려줍니다.

그리고 이 둘에게 차례로 일을 맡기는 중앙 노트북이 있습니다. 중앙 노트북의 그래프는 "슬랙 담당에게 요약 요청 → 받은 요약을 노션 담당에게 저장 요청" 두 단계뿐입니다. 2장과 3장에서 사람이 요약을 복사해 노션에 붙여 넣어야 했던 연결 고리를, 에이전트 사이의 요청과 응답이 대신하는 셈입니다. 이렇게 중앙 하나가 차례로 일을 맡기는 배치를 고른 이유와, 같은 A2A로 만들 수 있는 다른 배치는 4.2.3에서 비교합니다.

4.2MCP 다시 보기와 A2A

4.2.1MCP: 에이전트가 도구를 부르는 규칙

2장과 3장에서 쓴 MCP를 한 단락으로 되짚습니다. 모델은 함수를 직접 실행하지 못하고, 어떤 함수를 어떤 인자로 부를지 쓸 뿐이며 실행은 코드가 합니다(펑션 콜링). MCP는 그 함수의 정의와 실행 코드를 MCP 서버라는 별도 프로그램으로 옮기고, 앱은 MCP 클라이언트로 tools/list(도구 목록 요청)와 tools/call(도구 실행 요청)을 보내 도구를 쓰게 한 규칙입니다. 우리는 slack_mcp.py와 notion_mcp.py를 FastMCP로 만들었고, 노트북이 이 파일들을 하위 프로그램으로 띄워 표준 입출력(stdio)으로 대화했습니다. 3.1.3에서는 클라이언트 코드는 그대로 두고 서버만 바꿔 끼울 수 있다는 것도 확인했습니다.

여기서 MCP의 성격을 한 가지 짚어 두겠습니다. MCP 도구는 함수입니다. 이름과 입력 형식이 정해져 있고, 부르는 쪽이 "이 인자로 이 일을 해"라고 정확히 지시하면 그대로 실행해 결과를 돌려줍니다. slack_recent_messages는 시킨 기간의 메시지를 가져올 뿐, 그것을 어떻게 쓸지는 판단하지 않습니다. 판단은 도구를 부른 에이전트의 몫입니다.

4.2.2A2A: 에이전트가 에이전트에게 일을 맡기는 규칙

A2A(Agent2Agent)는 에이전트가 다른 에이전트에게 일을 맡기고 결과를 받는 방법을 정한 공개 규약입니다. 구글이 2025년에 처음 공개했고, 지금은 리눅스 재단 아래의 오픈 프로젝트로 관리됩니다. MCP와 무엇이 다른지는 "도구에게 시키는 것"과 "동료에게 맡기는 것"의 차이로 보면 분명해집니다.

4.2.3A2A에서 누가 누구를 부르는가

이 장의 그림들은 대부분 중앙 노트북 하나에 에이전트 둘이 매달린 모양입니다. 그래서 A2A가 "중앙에 있는 에이전트가 다른 에이전트들을 부르는 규칙"처럼 보이기 쉽지만, 그렇지 않습니다. A2A가 정하는 단위는 두 에이전트 사이의 한 번의 요청과 응답뿐입니다. 그 한 번의 대화에서 일을 맡기는 쪽을 클라이언트(client agent), 일을 맡는 쪽을 원격 에이전트(remote agent)라고 부릅니다. 이 두 이름은 대화마다 정해지는 자리일 뿐, 에이전트에게 붙는 고정된 신분이 아닙니다. 요청을 받는 서버로 떠 있는 에이전트라도 다른 에이전트의 카드를 읽고 요청을 보내는 순간 그 대화에서는 클라이언트가 됩니다.

규약에 "중앙"이라는 자리가 없으므로, 에이전트들을 어떤 모양으로 엮을지는 만드는 사람이 정합니다. 대표적인 배치는 그림 4.2의 세 가지입니다.

① 중앙 조율형은 이 장의 실습이 쓰는 배치입니다. 일을 맡기는 쪽은 언제나 중앙 하나이고, 두 에이전트는 원격 에이전트 역할만 합니다. 업무 순서와 실패 처리, 실행 기록이 모두 중앙 한곳에 모이므로 흐름을 읽고 고치기 쉽습니다. 두 에이전트는 서로의 존재를 모르기 때문에 각자 다른 흐름에서도 그대로 쓸 수 있습니다. 대신 슬랙 요약문이 노션 에이전트에게 가려면 반드시 중앙을 한 번 거쳐야 하고, 중앙이 멈추면 전체가 멈추며, 중앙이 모든 에이전트의 입력 모양을 알고 있어야 합니다.

② 직접 연결형에서는 일을 맡은 에이전트가 다음 에이전트를 직접 부릅니다. 중앙은 슬랙 요약 에이전트에게 "요약해서 노션에 남겨 줘"라고 한 번만 맡기고, 슬랙 요약 에이전트가 요약을 마친 뒤 노션 기록 에이전트의 카드를 읽고 저장을 요청합니다. 이때 슬랙 요약 에이전트는 중앙과의 대화에서는 원격 에이전트이고, 노션 에이전트와의 대화에서는 클라이언트입니다. 한 에이전트가 두 역할을 동시에 하는 것이 A2A에서는 자연스러운 일입니다. 중계가 줄어드는 대신, 슬랙 요약 에이전트가 노션 에이전트의 주소와 입력 모양을 알아야 하므로 두 에이전트가 서로 묶입니다.

③ 연쇄·계층형은 맡은 일을 다시 쪼개 아래 에이전트들에게 맡기는 배치입니다. 4.1.2의 주간 보고를 예로 들면, 중앙은 주간 보고 에이전트에게 "이번 주 보고서 만들어 줘"라고만 맡기고, 주간 보고 에이전트가 개발 현황 에이전트와 영업 실적 에이전트에게 각각 자료를 요청해 엮습니다. 회사에서 팀장이 받은 일을 팀원들에게 나누는 것과 같은 모양입니다. 4.2.2에서 말한 "상대의 속은 모른다"는 성질 덕분에, 중앙은 주간 보고 에이전트 아래에 에이전트가 몇 개 더 있든 알 필요가 없습니다. 계층이 깊어져도 위쪽의 코드는 단순하게 유지됩니다.

세 배치 모두 쓰는 규약은 똑같습니다. Agent Card로 상대를 알고, message/send로 일을 맡기고, Message나 Task로 결과를 받습니다(4.3). 달라지는 것은 누가 누구의 카드를 알고 있느냐뿐입니다. 이 장이 ①을 고른 것은 2장과 3장의 에이전트를 고치지 않고 서로 모르는 독립 부품으로 쓰기 위해서이고, 두 에이전트의 일이 노트북 한 화면의 기록으로 이어지는 모습을 보여 주기 위해서입니다. ②로 바꾸려면 무엇을 고치면 되는지는 4.4.4에서 다룹니다.

4.2.4MCP와 A2A는 함께 쓴다

A2A가 MCP를 대신하는 것은 아닙니다. 두 규칙은 서로 다른 방향의 연결을 맡고, 한 시스템 안에서 함께 쓰입니다. 이번 장의 구조를 이 관점으로 그리면 그림 4.3와 같습니다.

위쪽의 파란 연결이 A2A입니다. 중앙 노트북은 두 에이전트에게 "요약해 줘", "저장해 줘"라고 일을 맡깁니다. 아래쪽의 초록 연결이 MCP입니다. 각 에이전트는 맡은 일을 하기 위해 자기 MCP 서버의 도구를 부릅니다. 같은 도구라도 누가 부르는지가 2장·3장과 달라졌다는 점을 눈여겨보세요. 앞 장에서는 노트북이 MCP 클라이언트였지만, 이번에는 MCP 클라이언트가 각 에이전트 안으로 들어갔습니다. 중앙 노트북은 더 이상 슬랙 도구나 노션 도구를 직접 부르지 않습니다.

정리 · MCP는 에이전트가 도구를 부르는 규칙이고, A2A는 에이전트가 에이전트에게 일을 맡기는 규칙입니다. A2A에서 맡기는 쪽(클라이언트)과 맡는 쪽(원격 에이전트)은 요청마다 정해지는 자리이며, 중앙이라는 자리는 규약에 없습니다. 도구는 시킨 대로 실행하는 함수이고, 에이전트는 자기 판단과 도구와 권한을 가진 동료입니다. 그래서 한 시스템 안에서 A2A로 일을 나눠 맡기고, 맡은 쪽은 MCP로 도구를 쓰는 구조가 자연스럽게 만들어집니다.

4.3A2A의 구성 요소

A2A로 두 에이전트가 협업하려면 세 가지가 정해져 있어야 합니다. 일을 맡기는 쪽이 상대가 누구이고 무엇을 할 줄 아는지 알 방법(Agent Card), 일을 맡기는 요청의 모양(메시지), 그리고 결과를 돌려주는 방식(Message 응답과 Task)입니다. 이 절에서는 각각을 이번 실습의 실제 값으로 살펴보고, 마지막으로 이 규칙을 대신 처리해 주는 a2a-sdk 서버가 어떤 층으로 이뤄졌는지 봅니다.

4.3.1Agent Card: 에이전트의 소개서

사람끼리 일을 부탁할 때 상대의 부서와 담당 업무, 연락처를 먼저 알아야 하듯이, A2A에서도 일을 맡기는 쪽은 상대 에이전트의 소개서부터 읽습니다. 이 소개서가 Agent Card입니다. A2A 에이전트 서버는 자기 주소 아래의 정해진 경로 /.well-known/agent-card.json에 이 카드를 JSON으로 내놓습니다. 경로가 약속되어 있으므로 에이전트의 주소만 알면 누구든 카드를 읽어 볼 수 있습니다. 이번 실습의 슬랙 요약 에이전트가 내놓는 카드는 그림 4.4과 같습니다.

카드의 항목은 크게 다섯 갈래입니다. name과 description은 이 에이전트가 누구인지 알려 줍니다. 사람이 읽기도 하지만, 여러 에이전트 중 누구에게 일을 맡길지 모델이 고르게 할 때는 MCP 도구의 설명문처럼 모델이 읽는 안내문이 됩니다. url은 실제 요청을 보낼 주소이고, capabilities는 응답을 조금씩 흘려보내는 스트리밍을 지원하는지 같은 부가 능력을, defaultInputModes와 defaultOutputModes는 주고받는 내용의 형식을 밝힙니다. 이 실습의 에이전트는 스트리밍 없이 결과를 한 번에 돌려주고, 일반 텍스트(text/plain)를 주고받습니다.

마지막 skills가 이 에이전트가 할 줄 아는 일의 목록입니다. 여기서 MCP와의 차이가 하나 더 드러납니다. 슬랙 요약 에이전트 안에는 MCP 도구가 두 개(slack_recent_messages, slack_post_summary) 연결되어 있지만, 카드에 적힌 skill은 "슬랙 채널을 읽고 요약한다" 하나뿐입니다. skill은 에이전트가 가진 도구를 나열한 것이 아니라 바깥에 맡길 수 있다고 내세우는 업무입니다. 실제로 이 에이전트는 게시 도구를 갖고 있지만 쓰지 않고, 카드에도 밝히지 않습니다. 에이전트가 안에 무엇을 가졌는지와 밖에 무엇을 약속하는지가 분리되어 있다는 것, 이것이 4.2.2에서 말한 "상대의 속은 모른다"의 구체적인 모습입니다.

4.3.2메시지: 일을 맡기는 요청의 모양

카드로 상대의 주소를 알았으면 일을 맡깁니다. A2A의 요청은 HTTP로 보내는 JSON-RPC 2.0 형식의 메시지입니다. JSON-RPC는 "어떤 기능(method)을 어떤 인자(params)로 실행해 달라"는 요청과 그 응답을 JSON으로 주고받는 오래된 규칙으로, 요청마다 붙이는 id로 응답과 요청의 짝을 맞춥니다. A2A는 이 봉투 위에 "에이전트에게 메시지를 보낸다"는 기능 message/send를 정의해 두었습니다. 중앙 노트북이 슬랙 요약 에이전트에게 보내는 실제 요청과 돌아오는 응답을 나란히 놓으면 그림 4.5와 같습니다.

요청은 두 겹으로 되어 있습니다. 바깥은 JSON-RPC의 봉투입니다. id는 이 요청의 번호이고, method는 A2A가 정한 기능 이름 message/send입니다. 안쪽의 params.message가 에이전트에게 보내는 메시지 자체로, 누가 보냈는지(role이 user, 즉 일을 맡기는 쪽), 메시지의 번호(messageId), 그리고 내용물인 parts로 이뤄집니다. 요청 번호와 메시지 번호가 따로 있다는 점에 주의합니다. 앞의 것은 HTTP 요청 한 번을, 뒤의 것은 대화 속의 메시지 하나를 가리킵니다.

메시지의 내용물은 파트(part)의 목록입니다. A2A는 파트를 세 종류로 정해 두었습니다. 글을 담는 텍스트 파트(kind: "text"), 파일을 담는 파일 파트, 구조화된 JSON 데이터를 담는 데이터 파트입니다. 이 실습은 Agent Card에 text/plain을 주고받는다고 밝혔으므로 텍스트 파트 하나만 쓰고, 그 글자 안에 {"hours": 24}라는 JSON 문자열을 넣었습니다. 구조화된 값을 데이터 파트로 보내는 방법도 있지만, 텍스트 한 가지로 통일해 두면 양쪽 코드가 단순해집니다. 대신 받는 쪽이 이 글자를 다시 JSON으로 읽어야 한다는 약속이 생기고, 이 약속은 카드에 드러나지 않으므로 두 에이전트를 만드는 사람끼리 따로 맞춰야 합니다.

응답도 같은 봉투에 담겨 옵니다. id가 요청과 같은지로 "내가 보낸 요청에 대한 답"임을 확인하고, result에 결과가 들어 있습니다. 결과의 kind가 message이고 role이 agent이니, 에이전트가 메시지 하나로 답을 보냈다는 뜻입니다. 그 메시지의 텍스트 파트 안에 요약문, 수집 건수, 그리고 에이전트 내부의 실행 기록이 다시 JSON 문자열로 들어 있습니다. 실행 기록을 왜 함께 돌려보내는지는 4.4.3에서 설명합니다.

4.3.3Message 응답과 Task

A2A의 응답에는 두 종류가 있습니다. 위처럼 에이전트가 곧바로 Message 하나로 답하는 방식과, Task(작업)라는 객체를 돌려주는 방식입니다. Task는 오래 걸리는 일을 위한 것입니다. 에이전트가 "작업을 접수했다"며 작업 번호를 먼저 돌려주고, 작업은 상태를 바꿔 가며 진행되며, 일을 맡긴 쪽은 그 번호로 진행 상황을 다시 묻거나 결과물(artifact)을 받아 갑니다. a2a-sdk에 정의된 작업 상태는 다음과 같습니다.

이 실습은 Message 방식만 씁니다. 슬랙 요약은 몇 초면 끝나고, 노션 저장도 마찬가지라서 작업 번호를 주고받으며 기다릴 이유가 없기 때문입니다. 중앙 노트북은 요청을 보낸 뒤 응답이 올 때까지 기다렸다가, kind가 message가 아니면 오류를 냅니다. 회의 녹음 한 시간을 받아 적는 일처럼 오래 걸리는 작업이나, 중간에 사람에게 "이 내용으로 저장할까요?"라고 되묻는 작업(input-required)이라면 Task 방식을 쓰게 됩니다. 3장에서 사람의 확인을 그래프 밖에 두었던 것을, A2A에서는 이 상태로 표현할 수 있습니다.

4.3.4a2a-sdk 서버의 층

Agent Card를 내놓고, JSON-RPC 요청을 해석하고, 응답 봉투를 만드는 일을 직접 짜려면 꽤 많은 코드가 필요합니다. 이 실습은 A2A 프로젝트가 제공하는 파이썬 라이브러리 a2a-sdk로 이 부분을 맡기고, 우리는 "요청이 오면 무엇을 할지"만 작성합니다. 요청 하나가 서버 안에서 거치는 층은 그림 4.6와 같습니다.

맨 위의 uvicorn은 파이썬 웹 서버로, 정해진 주소와 포트에서 HTTP 요청을 받습니다. 그 아래 A2AStarletteApplication은 요청 경로를 보고 나눕니다. /.well-known/agent-card.json으로 온 요청에는 카드를 돌려주고, 기본 경로(/)로 온 POST 요청은 JSON-RPC로 해석해 아래로 넘깁니다. DefaultRequestHandler는 message/send 같은 A2A 기능을 실제로 처리하는 층입니다. 요청이 오면 우리가 넘겨준 실행기(executor)를 백그라운드에서 실행하고, 실행기가 내놓는 결과 이벤트를 기다렸다가 응답 봉투에 담아 돌려줍니다.

우리가 작성하는 것은 네 번째 층, AgentExecutor를 상속한 GraphExecutor입니다. a2a-sdk는 이 클래스의 execute()를 "요청이 왔을 때 할 일"로 부릅니다. 우리는 그 안에서 메시지의 텍스트를 꺼내 JSON으로 읽고, 2장의 그래프를 실행하고, 결과를 Message로 만들어 EventQueue(이벤트 줄)에 넣습니다. 실행기와 처리기가 함수 호출로 결과를 주고받지 않고 이벤트 줄을 거치는 이유는, 같은 구조로 Task의 상태 변화나 스트리밍처럼 결과가 여러 번에 나눠 나오는 경우까지 다루기 위해서입니다. 이 실습처럼 Message 하나만 넣으면, 처리기는 그 Message를 최종 결과로 보고 바로 응답합니다.

그 아래 두 층은 2장과 3장에서 만든 것이 그대로 들어갑니다. A2A 서버라는 겉옷만 새로 입혔을 뿐, 에이전트의 두뇌인 LangGraph 그래프와 손발인 MCP 도구는 앞 장의 코드입니다. 이 장에서 새로 쓰는 코드가 생각보다 적은 이유가 여기에 있습니다.

4.4이번 실습의 전체 구조

A2A의 구성 요소를 알았으니 이번 실습 전체를 조립해 봅니다. 구조는 세 가지 시선으로 보면 정리됩니다. 몇 개의 프로그램이 어떻게 연결되어 도는지(프로세스), 어느 그래프가 어느 그래프를 부르는지(그래프), 그리고 데이터가 그 경계를 어떻게 건너는지(상태)입니다.

4.4.1프로세스 다섯 개

2장과 3장의 실습은 프로그램 두 개로 돌았습니다. 노트북과, 노트북이 띄운 MCP 서버 하나입니다. 이번에는 다섯 개가 동시에 돕니다(그림 4.7).

①은 우리가 셀을 실행하는 Colab 노트북입니다. ②와 ③은 같은 파일 a2a_server.py를 서로 다른 역할(slack, notion)과 포트(9101, 9102)로 두 번 실행한 에이전트 서버입니다. 노트북이 subprocess.Popen으로 띄우며, 띄운 뒤에는 서로 독립된 프로그램이 됩니다. ④와 ⑤는 각 에이전트 서버가 다시 하위 프로그램으로 띄운 MCP 서버로, 2장과 3장의 파일 그대로입니다.

연결은 두 종류입니다. ①과 ②·③ 사이는 HTTP 위의 A2A이고, ②와 ④, ③과 ⑤ 사이는 표준 입출력 위의 MCP입니다. 노트북에서 MCP 클라이언트가 사라졌다는 점이 2장·3장과 가장 크게 다른 부분입니다. 노트북은 슬랙 API는 물론이고 슬랙 MCP 도구의 이름조차 쓰지 않습니다. 노트북이 아는 것은 두 에이전트의 주소와 주고받을 JSON의 모양뿐입니다.

에이전트 서버를 별도 프로세스로 띄우는 것은, 서버가 실행되는 동안 요청을 기다리며 계속 떠 있어야 하기 때문입니다. 실제 서비스라면 ②와 ③은 서로 다른 컴퓨터, 다른 팀의 클라우드에서 돌고 주소도 127.0.0.1이 아닌 공개 주소가 됩니다. 이 실습은 Colab 가상 머신 하나 안에서 그 구조를 축소해 보여 주는 것이고, 에이전트 서버가 127.0.0.1에서만 요청을 받게 해 두어 가상 머신 바깥에서는 접근할 수 없습니다.

4.4.2그래프 세 개

이번 실습에는 LangGraph 그래프가 세 개 있습니다. 중앙 노트북의 workflow, 슬랙 요약 에이전트 안의 slack_graph, 노션 기록 에이전트 안의 save 그래프입니다. 이 셋의 관계가 이 장의 구조를 가장 잘 보여 줍니다(그림 4.8).

위쪽 파란 점선 안이 중앙 노트북의 workflow입니다. 노드는 summarize와 save 두 개이고, 모양은 2장의 read → summarize와 다르지 않습니다. 다른 것은 노드 안에서 하는 일입니다. 2장과 3장의 노드는 MCP 도구를 부르거나 모델을 불렀지만, 이 두 노드는 도구도 모델도 부르지 않습니다. request_summary()는 슬랙 요약 에이전트에게, request_save()는 노션 기록 에이전트에게 A2A로 일을 맡기고 결과만 받아 옵니다. 노드가 하는 "한 단계의 일"이 직접 처리에서 위임으로 바뀐 것입니다.

아래쪽 두 점선 상자가 그 위임을 받는 에이전트 안의 그래프입니다. 왼쪽 slack_graph는 2장의 그래프 정의를 한 글자도 바꾸지 않고 서버 파일로 옮긴 것이고, 오른쪽 save 그래프는 3장의 저장 그래프에서 상태의 memo 칸만 뺀 것입니다. 중앙의 노드 하나가 아래 그래프 하나 전체를 실행시키는 셈이라, 그래프가 다른 그래프를 품는 두 층의 그래프가 됩니다. 다만 같은 프로그램 안에서 그래프를 노드로 끼워 넣는 것과 달리, 아래 그래프는 다른 프로세스에 있고 둘 사이를 잇는 것은 A2A 메시지입니다.

위아래를 잇는 화살표 옆의 이름을 보면 데이터가 어떻게 오가는지 보입니다. 중앙의 summarize 노드는 hours를 내려보내고 summary를 돌려받습니다. save 노드는 title과 text를 내려보내고 saved를 돌려받습니다. 이 화살표는 그래프의 엣지가 아닙니다. 엣지는 같은 그래프 안의 노드 순서이고, 이 화살표는 노드가 실행되는 동안 다른 프로세스와 주고받는 요청과 응답입니다. 중앙의 summarize 노드는 아래의 slack_graph가 END에 이르러 응답이 돌아올 때까지 끝나지 않고 기다립니다.

4.4.3상태가 프로세스를 건너는 방법

2장의 그래프에서 노드 사이의 데이터는 상태를 거쳐 저절로 전달됐습니다. 그런데 중앙의 WorkflowState와 에이전트의 SlackState는 서로 다른 프로세스의 메모리에 있어서, 상태끼리 직접 이어질 수 없습니다. 둘 사이를 잇는 것은 A2A 메시지 안의 JSON 문자열이고, 상태의 값을 JSON에 담고 다시 꺼내는 일은 코드가 손으로 합니다. 네 번의 건너기를 따라가면 그림 4.9과 같습니다.

①에서 중앙의 request_summary()는 상태의 hours를 꺼내 {"hours": 24}로 만들어 보냅니다. 슬랙 에이전트의 GraphExecutor는 이 글자를 JSON으로 읽어 그대로 slack_graph의 시작 입력으로 넣습니다. JSON의 키 이름 hours가 SlackState의 칸 이름과 같기 때문에 별다른 변환 없이 이어집니다. ②에서 에이전트는 그래프의 최종 상태에서 summary와 source["count"]만 골라 응답에 담고, 원문 전체가 든 source는 보내지 않습니다. 중앙은 그중 summary만 자기 상태에 넣습니다.

③에서는 이름이 바뀝니다. 중앙 상태의 summary가 JSON에서는 text라는 키로 보내지고, 노션 에이전트의 NoteState의 text 칸에 들어갑니다. 노션 기록 에이전트는 받은 글이 슬랙 요약인지 회의 메모인지 모르고 알 필요도 없습니다. 그저 "제목과 본문"을 받을 뿐입니다. 에이전트를 범용으로 만들려면 이렇게 받는 쪽의 말로 입력을 정하고, 이름을 맞추는 일은 맡기는 쪽이 하는 편이 좋습니다. 같은 노션 기록 에이전트를 3장의 회의 메모 정리에도, 다른 팀의 보고서 저장에도 그대로 쓸 수 있기 때문입니다.

④에서 노션 에이전트는 저장 결과(saved)를 통째로 돌려주고, 중앙의 request_save()도 받은 응답을 통째로 saved에 넣습니다. 그런데 이 응답에는 실행 기록(execution_log)이 함께 들어 있어서, 중앙의 최종 상태에 노션 에이전트의 기록까지 실리게 됩니다. ②에서 summary만 골라 넣은 것과 대조적입니다. 실제 실행 결과에서 이 차이가 어떻게 보이는지는 4.5.11에서 확인합니다.

실행 기록을 응답에 담아 보내는 이유도 여기서 짚어 둡니다. 2장과 3장에서는 모든 일이 한 노트북에서 일어나서 [도구 호출], [모델 입력] 같은 기록이 한 화면에 순서대로 찍혔습니다. 이번에는 도구 호출과 모델 호출이 에이전트 서버 안에서 일어나므로, 그 기록은 서버의 로그 파일에 찍힐 뿐 노트북 화면에는 나오지 않습니다. 요약이 이상할 때 원인을 찾으려면 서버 안을 들여다봐야 하는데, A2A의 원칙상 중앙은 에이전트의 속을 모르는 것이 정상입니다. 이 실습은 학습을 위해 에이전트가 자기 기록을 응답에 실어 보내고, 중앙이 그것을 [원격 …]이라는 이름으로 다시 찍게 했습니다. 여러 프로세스에 흩어진 기록을 한 줄로 이어 읽는 것으로, 실제 서비스에서는 이런 일을 분산 추적(distributed tracing) 도구가 맡습니다.

4.4.4설계 판단

이 구조에는 앞 장들과 다른 판단이 세 가지 들어 있습니다.

첫째, 사람의 확인 단계가 없습니다. 2장에서는 요약을 사람이 읽은 뒤에야 게시했고, 3장에서는 작성 그래프와 저장 그래프 사이에 확인 셀을 두었습니다. 이번 workflow는 요약이 오자마자 노션 저장을 요청하므로, 셀을 한 번 실행하면 확인 없이 노션에 문서가 생깁니다. "두 에이전트가 사람 손을 거치지 않고 일을 이어받는다"는 협업의 모습을 보여 주기 위한 선택이지만, 그만큼 요약이 틀렸을 때 그대로 문서로 남는 위험도 받아들인 것입니다. 실제 업무에 들인다면 4.3.3에서 말한 Task의 input-required 상태나, 3.4에서 말한 LangGraph의 중단 기능으로 저장 앞에 승인 단계를 다시 넣는 것을 검토해야 합니다.

둘째, 중앙 조율형 배치를 골랐습니다. 4.2.3에서 본 것처럼 같은 일을 직접 연결형으로도 만들 수 있습니다. 그렇게 바꾸려면 고칠 곳은 세 군데입니다. 4.5.10의 call_agent()를 a2a_server.py로 옮기고, 슬랙 요약 에이전트의 slack_graph에 요약 다음 노드로 "노션 기록 에이전트에게 저장을 맡기는" 노드를 하나 더 붙이고, 슬랙 요약 에이전트가 노션 에이전트의 주소를 알 수 있게 넘겨 주면 됩니다. 그러면 중앙 그래프는 노드 하나(summarize)로 줄고, 슬랙 요약 에이전트는 중앙에게는 원격 에이전트이면서 노션 에이전트에게는 클라이언트가 됩니다. 이 장이 그렇게 하지 않은 것은 슬랙 요약 에이전트를 "요약만 하는" 독립 부품으로 두어야 다른 흐름에서도 그대로 쓸 수 있고, 노션에 저장할지 말지 같은 업무 판단을 중앙 한곳에서 바꿀 수 있기 때문입니다.

셋째, 이 규모에서는 A2A가 꼭 필요하지 않습니다. 솔직히 말해 이번 실습의 일은 3장 끝의 확장 방향에서 말했듯이 노트북 하나에 두 MCP 서버를 연결하고 노드를 하나 더 붙이면 끝납니다. 프로세스도 다섯 개가 아니라 세 개면 됩니다. 2장에서 "MCP는 도구를 여러 앱이 나눠 쓸 때 가치가 드러난다"고 했던 것처럼, A2A도 다음과 같은 상황에서 가치가 드러납니다.

  • 에이전트의 주인이 다를 때 · 슬랙 요약 에이전트는 협업 도구 팀이, 노션 기록 에이전트는 문서 관리 팀이 각자 고치고 배포합니다.
  • 권한을 나눠야 할 때 · 각 에이전트가 자기 서비스의 토큰만 가지므로, 한쪽이 뚫려도 다른 서비스는 안전합니다.
  • 여러 곳에서 같은 에이전트를 쓸 때 · 노션 기록 에이전트 하나를 회의록, 주간 보고, 장애 기록 흐름이 함께 씁니다.
  • 만든 방식이 다를 때 · 한쪽은 LangGraph, 다른 쪽은 다른 프레임워크나 다른 언어로 만들어도 A2A 규칙만 지키면 협업할 수 있습니다.

이 실습은 그런 상황을 Colab 하나 안에서 흉내 낸 것입니다. 그래서 같은 가상 머신 안에서 돌기 때문에 생기는 한계도 있습니다. 노트북이 서버를 띄울 때 환경변수를 통째로 복사해 넘기므로(4.5.9), 슬랙 에이전트 프로세스에도 사실은 노션 토큰이 들어 있습니다. 각 에이전트가 자기 MCP 서버에는 자기 토큰만 넘기도록 짜여 있지만(4.5.8), 진짜 권한 분리는 에이전트를 서로 다른 환경에 따로 배포할 때 이뤄진다는 점을 기억해 두세요.

4.5[프로젝트] 슬랙 요약을 노션에 남기는 A2A 협업

이제 그림 4.7의 프로세스 다섯 개와 그림 4.8의 그래프 세 개를 코드로 만듭니다. 순서는 다음과 같습니다. 라이브러리를 설치하고 2장·3장에서 준비한 값을 입력한 뒤(4.5.1~4.5.3), 앞 장의 MCP 서버 두 개를 다시 작성합니다(4.5.4). 이어서 이 장의 핵심인 A2A 에이전트 서버 파일 a2a_server.py를 네 부분으로 나눠 작성하고(4.5.5~4.5.8), 두 서버를 띄워 Agent Card를 확인합니다(4.5.9). 마지막으로 중앙 노트북에서 A2A 요청 함수와 중앙 그래프를 만들어 실행하고(4.5.10~4.5.11), 저장 결과를 확인한 뒤 서버를 종료합니다(4.5.12).

코드의 상당 부분은 2장과 3장에서 본 것이므로, 같은 코드는 어느 절과 같은지 밝히고 달라지는 점만 설명합니다. 지면은 A2A 서버와 중앙 그래프에 집중하겠습니다.

4.5.1환경 설정

중앙 노트북에도 2.4.3의 기록 함수 네 개를 준비합니다. 이번에 노트북에서 실제로 쓰는 것은 log_step()과 run_graph_logged()입니다. log_step()은 A2A 요청·결과와 에이전트가 돌려보낸 원격 기록을 찍고, run_graph_logged()는 중앙 그래프를 실행합니다. 노트북에는 MCP 도구가 없으므로 invoke_tool_logged()는 부를 일이 없고, invoke_model_logged()는 바로 뒤의 모델 연결 확인에만 쓰입니다. 같은 네 함수를 에이전트 서버 파일에도 넣는데(4.5.5), 거기서는 네 함수가 모두 쓰입니다.

    try:
        result = await tool_map[name].ainvoke(arguments)
    except Exception as exc:
        log_step("도구 실패", {"name": name, "error": f"{type(exc).__name__}: {exc}"})
        raise
    log_step("도구 결과", {"name": name, "result": result})

async def invoke_model_logged(model, messages):
    log_step("모델 입력", messages)
    try:
        response = await model.ainvoke(messages)
    except Exception as exc:
        log_step("모델 실패", {"error": f"{type(exc).__name__}: {exc}"})
        raise
    log_step("모델 응답", {"content": response.content, "tool_calls": response.tool_calls})
    return response
async def run_graph_logged(graph, inputs, config=None):
    log_step("그래프 시작", inputs)
    final_state, interruptions = {}, ()
    try:
        async for mode, value in graph.astream(
            inputs, config=config, stream_mode=["updates", "values"],
        ):
            if mode == "values":
                final_state = value
            else:
                for node, output in value.items():
                    if node == "__interrupt__":
                        interruptions = output
                        log_step("사용자 확인 대기", output)
                    else:
                        log_step("노드 완료", {"node": node, "output": output})
    except Exception as exc:
        log_step("그래프 실패", {"error": f"{type(exc).__name__}: {exc}"})
        raise
    if interruptions:
        return {**final_state, "__interrupt__": interruptions}
    log_step("그래프 완료", final_state)
    return final_state

async def notion_read_page(page_id: str) -> str:
    """Notion 페이지의 모든 블록 페이지와 하위 블록을 읽습니다."""
    page_id = str(uuid.UUID(page_id))
    pending = [("fetch", page_id, None, 0)]
    blocks, text_parts = [], []
    while pending:
        action, value, cursor, depth = pending.pop()
        if action == "fetch":
            path = f"blocks/{value}/children"
            if cursor:
                path += "?" + urlencode({"start_cursor": cursor})
            data = await notion_api("GET", path)
            if data.get("has_more"):
                pending.append(("fetch", value, data["next_cursor"], depth))
            for block in reversed(data.get("results", [])):
                pending.append(("block", block, None, depth))
            continue
        block = value
        blocks.append({"depth": depth, "block": block})
        content = block.get(block["type"], {})
        if block["type"] == "table_row":
            text = " | ".join("".join(item.get("plain_text", item.get("text", {}).get("content", ""))
                                       for item in cell) for cell in content.get("cells", []))

                           for item in content.get("rich_text", []))

            text_parts.append(text)
        if block.get("has_children"):
            pending.append(("fetch", block["id"], None, depth + 1))
    return json.dumps({"page_id": page_id, "text": "\n".join(text_parts),
                       "blocks": blocks, "block_count": len(blocks)}, ensure_ascii=False)

            # API 한 요청의 배열 100개와 본문 500KB 한도에 맞춰 나눠 전송합니다.
            if batch and (len(batch) == 100 or size > 500_000):
                await notion_api("PATCH", f"blocks/{page['id']}/children", {"children": batch})
                saved_characters += sum(len(b["paragraph"]["rich_text"][0]["text"]["content"]) for b in batch)
                batch = []
            batch.append(block)
        if batch:
            await notion_api("PATCH", f"blocks/{page['id']}/children", {"children": batch})
            saved_characters += sum(len(b["paragraph"]["rich_text"][0]["text"]["content"]) for b in batch)
    except Exception as exc:
        raise RuntimeError(
            f"페이지는 생성됐지만 본문 저장 중 실패했습니다. url={page['url']}, "
            f"저장 확인된 문자 수={saved_characters}, 원인={type(exc).__name__}: {exc}"
        ) from exc
    return json.dumps({"id": page["id"], "url": page["url"], "created": True,
                       "saved_characters": saved_characters}, ensure_ascii=False)

def log_step(stage, data):
    # 메시지 객체도 읽을 수 있는 JSON 값으로 바꿔 출력과 기록에 함께 사용합니다.

    log_step("그래프 시작", inputs)
    final_state, interruptions = {}, ()
    try:
        async for mode, value in graph.astream(
            inputs, config=config, stream_mode=["updates", "values"],
        ):
            if mode == "values":
                final_state = value
            else:
                for node, output in value.items():
                    if node == "__interrupt__":
                        interruptions = output
                        log_step("사용자 확인 대기", output)
                    else:
                        log_step("노드 완료", {"node": node, "output": output})
    except Exception as exc:

        raise
    if interruptions:
        return {**final_state, "__interrupt__": interruptions}
    log_step("그래프 완료", final_state)
    return final_state

%%writefile -a a2a_server.py
class GraphExecutor(AgentExecutor):
    def __init__(self, graph, role):
        self.graph = graph
        self.role = role

    async def execute(self, context: RequestContext, event_queue: EventQueue):
        request_log = []
        trace_token = current_execution_log.set(request_log)
        try:
            payload = json.loads(context.get_user_input())
            log_step("A2A 작업 접수", {"role": self.role, "input": payload})
            result = await run_graph_logged(self.graph, payload)
            output = ({"summary": result["summary"], "count": result["source"]["count"]}
                      if self.role == "slack" else dict(result["saved"]))
            output["execution_log"] = request_log
            await event_queue.enqueue_event(
                new_agent_text_message(json.dumps(output, ensure_ascii=False))
            )
        except Exception as exc:
            raise ServerError(error=InternalError(
                message=f"{self.role} 에이전트 실행 실패: {type(exc).__name__}: {exc}",
                data={"execution_log": request_log},
            )) from exc
        finally:
            current_execution_log.reset(trace_token)

    async def cancel(self, context: RequestContext, event_queue: EventQueue):
        raise NotImplementedError("이 Message 응답 예제에는 Task 취소 기능이 없습니다.")

① 이 요청만의 빈 기록 목록 request_log를 만들어 문맥 변수 current_execution_log에 등록합니다. set()은 이전 값을 되돌릴 때 쓸 표(trace_token)를 돌려주는데, 이것을 받아 두었다가 마지막 finally에서 reset()으로 원래 값을 되돌립니다. 이제부터 이 요청을 처리하는 동안 log_step()이 남기는 기록은 모두 request_log에도 쌓입니다.

② context.get_user_input()은 들어온 메시지의 텍스트 파트들을 꺼내 줄바꿈으로 이어 붙인 문자열을 돌려주는 a2a-sdk의 메서드입니다. 중앙 노트북이 텍스트 파트 하나에 JSON 문자열을 넣어 보내기로 약속했으므로(4.3.2), 이 문자열을 json.loads()로 읽으면 슬랙 역할에서는 {"hours": 24}, 노션 역할에서는 {"title": …, "text": …}가 나옵니다. 약속과 다른 글이 오면 여기서 JSON 오류가 나고, 오른쪽의 오류 경로로 갑니다.

③④ 받은 입력을 [A2A 작업 접수]로 기록하고, 그 사전을 그대로 그래프의 시작 입력으로 넣어 run_graph_logged()로 실행합니다. 그림 4.9의 ①과 ③이 이루어지는 곳입니다. 실행기는 그래프 안에서 무슨 일이 일어나는지 모릅니다. 슬랙이면 조회와 요약이, 노션이면 저장이 일어나지만, 실행기 코드는 두 역할에서 똑같습니다.

⑤⑥ 그래프의 최종 상태에서 바깥에 돌려줄 값만 고릅니다. 슬랙 역할은 요약문과 수집 건수만 담고, 원문 전체가 든 source는 담지 않습니다. 노션 역할은 저장 결과 saved를 dict()로 한 번 복사해 담는데, 바로 다음 줄에서 이 사전에 execution_log를 더하므로 그래프 상태의 원래 사전까지 바뀌지 않게 하려는 것입니다. 마지막으로 이 요청의 기록 request_log를 execution_log라는 키로 붙입니다.

⑦ 완성한 사전을 JSON 문자열로 바꿔 new_agent_text_message()로 감쌉니다. 이 도우미는 텍스트 파트 하나를 담고 role이 agent인 Message를 만들어 줍니다. 이것을 event_queue에 넣으면, 4.3.4에서 본 대로 DefaultRequestHandler가 이 Message를 최종 결과로 받아 그림 4.5 오른쪽의 응답으로 돌려보냅니다.

오류 경로. ②~⑥ 중 어디서든 예외가 나면, 원래 예외를 a2a-sdk의 ServerError로 감싸 다시 던집니다. 안에 담은 InternalError는 JSON-RPC 규칙의 "서버 내부 오류"(코드 -32603)이고, a2a-sdk가 이것을 JSON-RPC 오류 응답으로 바꿔 돌려줍니다. 눈여겨볼 곳은 data에 그때까지의 기록 request_log를 담는다는 점입니다. 성공 응답에 기록을 실어 보내듯 실패 응답에도 기록을 실어 보내므로, 중앙 노트북은 에이전트 안의 어느 단계에서 멈췄는지를 오류와 함께 볼 수 있습니다. 4.5.10의 call_agent()가 이 기록을 꺼내 찍습니다.

cancel()은 진행 중인 Task를 취소해 달라는 요청(tasks/cancel)이 왔을 때 불립니다. 이 실습은 Task를 만들지 않고 Message로 바로 답하므로 취소할 작업이 없어, 지원하지 않는다는 예외만 냅니다. AgentExecutor를 상속하면 이 메서드도 반드시 정의해야 해서 자리만 채운 것입니다.

servers에는 실행한 서버 프로세스를, logs에는 각 서버의 로그 파일을 역할 이름으로 보관합니다. 그냥 servers = {}로 만들지 않고 globals().setdefault()를 쓴 것은 이 셀을 다시 실행할 때를 위해서입니다. servers = {}였다면 다시 실행하는 순간 이미 떠 있는 서버를 가리키던 사전이 빈 사전으로 바뀌어, 서버는 계속 떠서 포트를 차지하는데 노트북은 그 서버를 끌 방법을 잃습니다. setdefault()는 같은 이름이 이미 있으면 기존 사전을 그대로 돌려주므로 그런 일이 생기지 않습니다.

def stop_servers():
    for process in servers.values():
        if process.poll() is None:
            process.terminate()
            try:
                process.wait(timeout=8)
            except subprocess.TimeoutExpired:
                process.kill()
                process.wait(timeout=5)
    for handle in logs.values():
        handle.close()
    servers.clear()
    logs.clear()

보관한 서버를 모두 끄는 함수입니다. 아직 실행 중인 프로세스(poll()이 None)에는 먼저 terminate()로 정상 종료를 요청하고 8초까지 기다립니다. 그래도 끝나지 않으면 kill()로 강제로 끝냅니다. 그다음 로그 파일을 닫고 두 사전을 비웁니다. 서버를 다시 띄우기 전과 실습을 마칠 때 이 함수를 부릅니다.

서버 실행. 역할마다 로그 파일을 열고 subprocess.Popen()으로 python -u a2a_server.py 역할 포트를 실행합니다. -u는 출력을 모아 두지 말고 바로바로 내보내라는 옵션으로, 서버가 찍는 기록이 로그 파일에 즉시 나타나게 합니다. 환경변수는 노트북의 것을 통째로 복사해 넘기고, 한글 기록이 깨지지 않도록 PYTHONIOENCODING을 utf-8로 정합니다. 서버의 표준 출력은 로그 파일로, 오류 출력도 같은 파일로 보냅니다.

준비 확인. Popen()은 프로세스를 띄우자마자 돌아오지만, 서버가 요청을 받을 준비를 마치려면 시간이 걸립니다. 그래서 각 서버의 Agent Card 주소에 0.5초마다 요청을 보내, 200 응답이 올 때까지 기다립니다. 4.5.8에서 본 대로 서버는 MCP 서버 연결을 마친 뒤에야 웹 서버를 시작하므로, 카드가 응답한다는 것은 MCP 도구까지 준비됐다는 뜻입니다(그림 4.11).

확인 반복문은 서버 프로세스가 살아 있는 동안만 돕니다(while servers[role].poll() is None). 서버가 시작 도중 오류로 죽으면 반복이 끝나고 ready가 False로 남으므로, 모든 서버를 정리한 뒤 어느 로그 파일을 보면 되는지 알려 주는 오류를 냅니다. 토큰이 틀렸거나 MCP 서버 파일이 잘못 만들어졌다면 a2a_slack.log나 a2a_notion.log에 서버 쪽 오류가 남아 있습니다. 실행 결과에 두 서버의 준비 완료가 차례로 찍혔으니, 이제 두 에이전트가 각자의 포트에서 일을 기다리고 있습니다.

4.5.10중앙 그래프와 A2A 호출

이제 중앙 노트북 쪽입니다. 에이전트에게 일을 맡기는 함수 하나를 만들고, 그 함수를 쓰는 노드 두 개로 그림 4.8 위쪽의 workflow를 만듭니다.

import uuid
import httpx

async def call_agent(base_url: str, payload: dict) -> dict:
    log_step("A2A 요청", {"url": base_url, "input": payload})
    request_id = str(uuid.uuid4())
    body = {
        "jsonrpc": "2.0", "id": request_id, "method": "message/send",
        "params": {"message": {
            "role": "user", "messageId": str(uuid.uuid4()),
            "parts": [{"kind": "text", "text": json.dumps(payload, ensure_ascii=False)}],
        }},
    }
    try:
        async with httpx.AsyncClient(timeout=None) as client:
            response = await client.post(base_url, json=body)
        response.raise_for_status()
    except Exception as exc:
        log_step("A2A 통신 실패", {"url": base_url, "error": f"{type(exc).__name__}: {exc}"})
        raise
    data = response.json()
    if "error" in data:
        for entry in (data["error"].get("data") or {}).get("execution_log", []):
            log_step("원격 " + entry["stage"], entry["data"])
        log_step("A2A 작업 실패", data["error"])
        raise RuntimeError(f"A2A 요청 실패: {data['error']}")
    if data.get("id") != request_id:
        raise RuntimeError("A2A 응답의 요청 ID가 일치하지 않습니다.")
    result = data["result"]
    if result.get("kind") != "message":
        raise RuntimeError("이 실습은 즉시 반환되는 Message 응답을 사용합니다.")
    text = "\n".join(part["text"] for part in result["parts"] if part.get("kind") == "text")
    output = json.loads(text)
    for entry in output.get("execution_log", []):
        log_step("원격 " + entry["stage"], entry["data"])
    log_step("A2A 결과", {k: v for k, v in output.items() if k != "execution_log"})
    return output

call_agent()는 에이전트의 주소와 맡길 일(payload)을 받아, 그림 4.5의 요청을 만들어 보내고 응답을 검사해 결과 사전을 돌려줍니다. 순서대로 보겠습니다.

요청 만들기. 먼저 [A2A 요청]으로 어디에 무엇을 맡기는지 기록합니다. 요청 번호와 메시지 번호를 uuid.uuid4()로 각각 새로 만들고, 맡길 일은 json.dumps()로 문자열로 바꿔 텍스트 파트 하나에 넣습니다. 4.3.2에서 본 두 겹, JSON-RPC 봉투와 그 안의 A2A 메시지가 이 사전에 그대로 들어 있습니다. 이것을 에이전트 주소로 POST합니다. Agent Card의 url이 곧 JSON-RPC 요청을 받는 주소입니다.

통신 오류 확인. 서버가 꺼져 있거나 HTTP 상태 코드가 실패를 알리면 [A2A 통신 실패]를 남기고 오류를 던집니다. 여기서 걸리는 것은 "에이전트에게 닿지 못한" 경우입니다.

작업 오류 확인. 닿기는 했지만 에이전트가 일을 하다 실패하면, 응답 본문에 result 대신 error가 들어 옵니다. JSON-RPC는 처리 결과의 성공과 실패를 HTTP 상태가 아니라 본문으로 알리는 규칙이라, 2장의 슬랙 API가 본문의 ok로 실패를 알리던 것과 비슷한 구조입니다. 이때 4.5.7의 실행기가 error.data에 담아 보낸 원격 기록을 하나씩 꺼내 [원격 …]으로 찍은 뒤, [A2A 작업 실패]를 남기고 오류를 던집니다. 오류 메시지만 보는 것이 아니라, 에이전트 안에서 어디까지 진행되다 멈췄는지를 노트북 화면에서 바로 볼 수 있게 한 것입니다.

응답 검사. 성공 응답이면 두 가지를 확인합니다. 응답의 id가 보낸 요청 번호와 같은지, 그리고 결과의 kind가 message인지입니다. 4.3.3에서 말했듯이 이 실습은 Message 응답만 다루므로, 에이전트가 Task를 돌려주면 처리할 방법이 없어 오류를 냅니다.

결과 꺼내기. 메시지의 텍스트 파트들을 이어 붙여 JSON으로 읽으면 에이전트가 돌려준 사전이 나옵니다. 그 안의 execution_log를 하나씩 [원격 …]으로 다시 찍고, 기록을 뺀 나머지를 [A2A 결과]로 남깁니다. 다만 함수가 돌려주는 output에는 execution_log가 그대로 남아 있습니다. 4.4.3에서 예고한 차이가 여기서 생깁니다.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class WorkflowState(TypedDict):
    hours: float | None
    title: str
    summary: str
    saved: dict

중앙 그래프의 상태입니다. 그림 4.8 오른쪽 위의 네 칸으로, hours와 title은 사람이 넣는 시작 입력이고, summary는 슬랙 요약 에이전트의 결과로, saved는 노션 기록 에이전트의 결과로 채워집니다. 3장의 NoteState와 비교하면 memo 대신 hours가, text 대신 summary가 있습니다. 회의록의 재료가 사람이 적은 메모에서 슬랙 대화로 바뀐 것입니다.

async def request_summary(state: WorkflowState):
    result = await call_agent(SLACK_AGENT_URL, {"hours": state.get("hours")})
    return {"summary": result["summary"]}

첫 번째 노드입니다. 상태의 hours를 꺼내 슬랙 요약 에이전트에게 맡기고, 돌아온 결과에서 summary만 골라 {"summary": …}로 돌려줍니다. 2장의 read_slack()과 나란히 놓으면 차이가 분명합니다. read_slack()은 MCP 도구 이름과 인자를 알아야 했지만, 이 노드는 에이전트의 주소와 {"hours": …}라는 입력 모양만 압니다. 요약이 어떤 도구와 모델로 만들어지는지는 이 노드의 관심 밖입니다.

async def request_save(state: WorkflowState):
    result = await call_agent(NOTION_AGENT_URL, {
        "title": state["title"], "text": state["summary"],
    })
    return {"saved": result}

두 번째 노드입니다. 상태의 title과 summary를 노션 기록 에이전트에게 보내는데, 그림 4.9의 ③처럼 summary를 text라는 키로 바꿔 보냅니다. 노션 에이전트가 정한 입력 모양에 맡기는 쪽이 맞추는 것입니다. 돌아온 결과는 고르지 않고 통째로 saved에 넣습니다. 앞 노드는 필요한 값만 골랐고 이 노드는 통째로 넣었다는 차이가, 실행 결과에서 어떻게 드러나는지 곧 확인합니다.

builder = StateGraph(WorkflowState)
builder.add_node("summarize", request_summary)
builder.add_node("save", request_save)
builder.add_edge(START, "summarize")
builder.add_edge("summarize", "save")
builder.add_edge("save", END)
workflow = builder.compile()

두 노드를 START → summarize → save → END로 잇고 컴파일합니다. 노드 이름 summarize가 슬랙 에이전트 안의 노드 이름과 같지만, 서로 다른 그래프의 다른 노드입니다. 중앙의 summarize는 "요약을 맡긴다", 에이전트 안의 summarize는 "모델로 요약한다"입니다. 실행 기록에서 중앙의 것은 [노드 완료]로, 에이전트 안의 것은 [원격 노드 완료]로 찍히므로 구분할 수 있습니다.
