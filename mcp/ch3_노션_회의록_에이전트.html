노션 회의록 에이전트 · LangGraph와 MCP로 만드는 회의록 작성·저장 봇

회의 메모를 회의록으로 정리해 노션 문서로 저장하고, 저장된 내용까지 다시 읽어 검증하는 MCP 도구 에이전트

회의가 끝나면 손에 남는 것은 대개 급하게 적은 메모입니다. "화면 초안 화요일 검토, 민수 초안, 지수 테스트, 예산 담당 미정"처럼 본인만 알아보는 줄임말이 섞여 있고, 결정된 것과 아직 정하지 못한 것이 뒤섞여 있습니다. 이 메모를 팀이 함께 보는 문서로 옮기려면 누군가 항목을 나누고, 문장을 다듬고, 노션에 새 페이지를 만들어 붙여 넣어야 합니다. 이 장에서는 이 일을 AI에게 맡겨, 회의 메모를 결정 사항·담당자별 할 일·미정 사항으로 정리한 뒤 노션에 새 회의록 문서로 저장하는 봇을 만듭니다.

2장의 슬랙 봇과 뼈대는 같습니다. 외부 서비스의 API를 MCP 서버의 도구로 감싸고, 노트북은 MCP 클라이언트로 그 도구를 이름으로 부르며, LangGraph가 작업 순서를 잡습니다. 달라지는 것은 상대하는 서비스입니다. 슬랙의 채널은 메시지가 시간순으로 쌓인 평평한 목록이지만, 노션의 문서는 블록 안에 블록이 들어가는 나무 구조입니다. 제목과 본문이 저장되는 자리도 다르고, 한 번에 보낼 수 있는 글자 수에도 제한이 있습니다. 그래서 같은 MCP 서버라도 문서를 읽는 도구와 쓰는 도구의 속이 슬랙 때보다 훨씬 많은 일을 해야 합니다.

이 장은 먼저 2장의 펑션 콜링과 MCP를 짧게 되짚고, 2장의 MCP 클라이언트 코드가 거의 그대로 노션 서버에 붙는다는 점을 확인합니다. 이어서 이번 장의 핵심인 노션의 데이터 구조와 권한 구조를 살펴본 뒤, 회의록 작성과 저장을 두 개의 그래프로 나눈 이유를 설명하고 프로젝트로 들어갑니다.

이 장을 마치면 다음을 할 수 있습니다.

  • 펑션 콜링과 MCP의 역할 분담을 다시 설명하고, MCP 서버만 바꿔 끼우면 클라이언트 코드는 그대로 쓸 수 있다는 점을 코드로 확인할 수 있습니다.
  • 노션의 페이지·속성·블록 구조를 설명하고, 문서를 읽을 때 하위 블록까지 따라 내려가야 하는 이유와 문서를 만들 때 요청이 두 번 필요한 이유를 설명할 수 있습니다.
  • 노션 연결(integration)의 토큰·기능·페이지 사용 권한을 설정하고, 401·403·404 오류가 각각 어느 단계의 문제인지 구분할 수 있습니다.
  • 노션 API의 길이 제한을 지키며 본문을 나눠 저장하는 MCP 도구를 만들고, 저장된 문서를 다시 읽어 제목·본문·위치를 검증할 수 있습니다.

실습은 2장과 같이 Google Colab에서 진행합니다. OpenAI API 키와 노션 계정(무료 요금제로 충분합니다)이 필요하고, 모델은 gpt-4.1-mini를 사용합니다.

3.1펑션 콜링과 MCP 다시 보기

2장에서 펑션 콜링과 MCP를 자세히 다뤘으므로, 여기서는 이번 장을 읽는 데 꼭 필요한 뼈대만 다시 정리합니다. 그리고 2장에서 말로만 했던 MCP의 장점, 즉 "같은 클라이언트로 다른 서버를 쓸 수 있다"는 점을 이번 장의 코드로 직접 확인합니다.

3.1.1모델은 쓰고, 코드는 실행한다

LLM은 글을 읽고 글을 쓰는 모델입니다. 노션에 페이지를 만들거나 문서를 검색하는 일은 노션 API에 네트워크 요청을 보내야 하는 일이라, 모델 혼자서는 할 수 없습니다. 펑션 콜링은 이 간극을 메우는 방법입니다. 개발자가 쓸 수 있는 함수의 목록을 이름·설명·매개변수로 적어(함수 정의) 모델에게 건네면, 모델은 요청을 읽고 "이 함수를 이 인자로 부르면 된다"는 호출 요청을 JSON으로 써서 내놓습니다. 그 요청을 받아 실제 함수를 실행하는 것은 앱의 코드입니다.

2장의 비유를 다시 쓰면, 모델은 처방전을 쓰는 의사이고 약을 짓는 것은 약국(앱의 코드)입니다. 모델이 함수를 고를 때 보는 것은 함수의 실제 코드가 아니라 함수 정의뿐이므로, 정의의 설명(description)을 언제 쓰는 함수인지 알 수 있게 적는 것이 중요합니다. 이 원칙은 이번 장에서 노션 도구 세 개의 설명문을 쓸 때도 그대로 적용됩니다.

3.1.2MCP는 정의와 실행을 앱 밖에 둔다

직접 펑션 콜링에서는 함수 정의와 실행 코드가 모두 앱 안에 있습니다. MCP(Model Context Protocol)는 이 두 가지를 MCP 서버라는 별도 프로그램으로 옮기고, 앱에는 서버와 대화하는 MCP 클라이언트만 남깁니다(그림 3.1). 클라이언트가 서버에 보내는 요청은 사실상 두 가지입니다. tools/list로 "어떤 도구가 있는지"를 묻고, tools/call로 "이 도구를 이 인자로 실행해 달라"고 맡깁니다.

주황색 두 칸이 앱에서 서버로 옮겨 간 부분입니다. 모델 쪽은 아무것도 달라지지 않습니다. 모델은 여전히 도구의 이름·설명·입력 형식을 보고 호출 요청을 쓸 뿐이고, 그 정의가 앱이 직접 쓴 것인지 서버에서 받아 온 것인지는 알지 못합니다. 2장에서 정리했듯이 MCP는 펑션 콜링을 대신하는 기술이 아니라, 도구를 앱 밖에 두고 정해진 규칙으로 꺼내 쓰는 방식입니다.

서버를 만드는 쪽에서 기억할 것도 두 가지입니다. 첫째, 서버는 FastMCP로 만들고 함수 위에 @mcp.tool()을 붙이면 도구로 등록됩니다. 이때 함수 이름이 도구 이름이, docstring이 도구 설명이, 매개변수의 타입 표시가 입력 형식이 됩니다. 둘째, 이 장의 서버도 노트북이 하위 프로그램으로 실행하는 파이썬 파일 하나이고, 둘은 표준 입출력(stdio)으로 요청과 응답을 주고받습니다.

3.1.3서버만 바꿔 끼우기

2장의 끝에서 "MCP의 가치는 같은 도구를 여러 앱이 나눠 쓸 때 드러난다"고 했습니다. 이번 장에서는 그 반대 방향, 즉 같은 클라이언트가 다른 서버를 쓰는 경우를 직접 겪게 됩니다. 2장의 노트북 코드와 이번 장의 노트북 코드를 나란히 놓으면, 슬랙 서버를 꽂았던 자리에 노션 서버를 꽂은 것과 다르지 않습니다(그림 3.2).

노트북 쪽에서 바뀌는 곳은 서버 설정 사전 하나뿐입니다. 구체적으로 짚으면 다음과 같습니다.

노트북은 노션 API의 주소도, 요청 형식도, 인증 머리말의 모양도 모릅니다. 그런 것은 모두 서버 파일 안에 있습니다. 노트북이 아는 것은 서버가 tools/list로 알려 준 도구 이름과 인자뿐입니다. 그래서 이번 장에서 새로 공부할 내용은 대부분 서버 파일 안쪽, 즉 노션 API를 어떻게 다뤄야 하는지에 몰려 있습니다. 다음 두 절에서 그 배경이 되는 노션의 데이터 구조와 권한 구조를 봅니다.

정리 · 모델은 도구 정의를 보고 호출 요청을 쓰고, 실행은 코드가 합니다. MCP는 그 정의와 실행 코드를 서버로 옮긴 것이고, 덕분에 클라이언트는 서버가 무엇을 상대하는지 몰라도 됩니다. 2장의 클라이언트 코드가 이번 장에 그대로 쓰이는 것이 그 증거입니다.

3.2노션의 데이터 구조

2장의 슬랙 조회 도구는 비교적 단순했습니다. 채널의 메시지는 시간순으로 늘어선 목록이고, 메시지 하나하나에 본문 문자열(text)이 들어 있어서, 목록을 끝까지 넘겨 받기만 하면 됐습니다. 노션은 다릅니다. 노션 API를 처음 다루는 사람이 가장 많이 헤매는 지점이 바로 "문서의 글이 어디에 들어 있는가"이므로, 서버 코드를 보기 전에 구조부터 정리하겠습니다.

3.2.1페이지, 속성, 블록

노션의 문서 하나는 API에서 페이지(page) 객체입니다. 그런데 페이지 객체를 받아 보면 본문이 들어 있지 않습니다. 페이지에는 ID, 주소, 상위 위치(parent), 그리고 속성(properties)이 있을 뿐이고, 문서의 제목은 이 속성 중 하나(type이 title인 속성)에 들어 있습니다. 본문은 페이지에 딸린 블록(block)들의 목록으로 따로 저장됩니다(그림 3.3).

그림 왼쪽은 GET /v1/pages/{id}로 받는 페이지 객체이고, 오른쪽은 GET /v1/blocks/{id}/children으로 받는 본문 블록입니다. 같은 문서인데 요청하는 주소가 다릅니다. 블록에는 문단(paragraph), 제목(heading_3), 글머리 목록(bulleted_list_item), 토글(toggle), 표(table) 같은 종류(type)가 있고, 종류 이름과 같은 이름의 칸 안에 실제 내용이 들어 있습니다. 문단 블록이라면 block["paragraph"]["rich_text"]에 글이 있는 식입니다.

여기에 두 가지가 더 얹힙니다. 첫째, 블록 안에 블록이 들어갈 수 있습니다. 토글 블록을 펼치면 보이는 글, 표 블록 안의 각 행이 그 예입니다. 이런 블록은 has_children이 true이고, 그 안의 블록은 부모 페이지의 children을 요청해서는 나오지 않습니다. 해당 블록의 ID로 children을 다시 요청해야 합니다. 둘째, 글은 문자열 하나가 아니라 rich_text라는 조각의 배열로 저장됩니다. 한 문장 안에서 일부만 굵게 하거나 링크를 걸 수 있도록 서식이 같은 구간마다 조각을 나누기 때문입니다. 그래서 글을 꺼낼 때는 조각들의 plain_text를 이어 붙여야 하고, 이것은 제목 속성에서도 마찬가지입니다.

3.2.2읽기와 쓰기에 미치는 영향

이 구조 때문에 이번 장의 서버 코드에는 슬랙 때 없던 일이 생깁니다. 이 장에서 설명하는 노션 API의 한도는 서버 코드의 주석과 노션 공식 문서에 적힌 값입니다.

읽을 때는 나무를 따라 내려가야 합니다. 페이지의 children을 받고, 그중 has_children이 있는 블록이 보이면 그 블록의 children을 또 받는 일을 더 내려갈 곳이 없을 때까지 반복해야 문서 전체의 글이 모입니다. 게다가 children 요청 하나도 한 번에 다 오지 않고 여러 쪽으로 나뉘어 올 수 있으므로, 2장의 슬랙 조회처럼 next_cursor로 다음 쪽을 이어 받아야 합니다. 쪽 넘기기와 나무 따라가기가 겹치는 셈입니다. 이것을 처리하는 notion_read_page()는 3.5.7에서 단계별로 따라가 봅니다.

쓸 때는 요청이 두 번 필요합니다. 제목은 페이지의 속성이고 본문은 블록이므로, 새 회의록을 만들려면 먼저 제목과 상위 위치를 담아 페이지를 만들고(POST /v1/pages), 돌아온 새 페이지의 ID에 본문 블록을 붙입니다(PATCH /v1/blocks/{id}/children). 페이지를 만들 때 본문을 함께 실어 보내는 방법도 있지만, 이 장의 코드는 두 단계를 나눠 두었습니다. 본문이 길어져 여러 번 나눠 보내야 할 때도 같은 붙이기 요청을 되풀이하면 되기 때문입니다(그림 3.4).

두 요청으로 나뉜다는 것은, 둘 사이에서 실패할 수 있다는 뜻이기도 합니다. ①은 성공하고 ②가 실패하면 노션에는 제목만 있는 빈 페이지가 남습니다. 노션 API에는 두 요청을 하나로 묶어 "둘 다 성공하거나 둘 다 없던 일로" 만드는 기능이 없으므로, 코드가 할 수 있는 일은 무엇이 어디까지 저장됐는지 정확히 알려 주는 것입니다. 3.5.7의 저장 도구가 실패할 때 만든 페이지의 주소와 저장이 확인된 글자 수를 오류 메시지에 담는 것은 이 때문입니다. 사람이 그 주소를 열어 빈 페이지를 지우거나 나머지를 채울 수 있습니다.

3.2.3한 번에 보낼 수 있는 양

노션 API에는 요청 하나에 담을 수 있는 양에 제한이 있습니다. 이 장의 저장 도구가 지키는 한도는 세 가지입니다.

한도값저장 도구의 대응
rich_text 조각 하나의 글자 수2,000자제목과 본문을 2,000자씩 잘라 조각·블록 하나에 하나씩 담습니다.
children 배열 하나의 블록 수100개블록이 100개 모이면 그때까지를 한 번에 보냅니다.
요청 본문 하나의 크기500KB다음 블록을 더했을 때 500KB를 넘으면 그 전까지를 보냅니다.

세 번째 한도는 한국어 문서에서 특히 중요합니다. 파이썬의 len()은 글자 수를 세지만 네트워크로 나가는 것은 UTF-8 바이트이고, 한글은 한 글자가 3바이트입니다. 한글 2,000자를 담은 문단 블록 하나를 이 장의 코드와 같은 방식으로 JSON으로 만들어 보면 약 6,100바이트가 됩니다. 그래서 한글로 꽉 찬 블록은 100개에 이르기 전에 81개째에서 500KB를 넘습니다. 영문이라면 100개를 다 채워 보낼 수 있는 양입니다. 저장 도구가 블록 개수만 세지 않고 요청 크기를 바이트로 다시 재는 이유가 여기에 있습니다. 이번 실습의 회의록은 117자라 이 한도에 한참 못 미치지만, 실제 회의록은 이보다 훨씬 길어질 수 있습니다.

지금까지의 차이를 2장의 슬랙과 나란히 정리하면 다음과 같습니다. 이번 장 서버 코드가 슬랙 때보다 긴 이유가 이 표에 모두 들어 있습니다.

3.3노션 연결과 권한 구조

슬랙에서는 앱을 만들고, 권한(scope)을 고르고, 봇을 채널에 초대했습니다. 노션도 비슷한 세 단계를 거치지만 이름과 순서가 조금 다릅니다. 노션에서 코드가 문서에 접근하는 주체는 연결(connection, 영문 문서에서는 integration)입니다. 이 장에서는 classroom-agent라는 연결을 만들고, 코드는 이 연결의 API 토큰으로 요청을 보냅니다.

요청 하나가 노션 문서에 닿기까지는 세 겹의 확인을 통과해야 합니다(그림 3.5). 어느 겹에서 막혔는지에 따라 돌아오는 오류가 다르므로, 이 그림을 기억해 두면 오류를 보고 바로 어디를 고칠지 알 수 있습니다.

① API 토큰은 "누가 보낸 요청인가"를 확인합니다. 토큰이 틀렸거나 일부만 복사됐으면 401 오류가 납니다. ② 기능(capabilities)은 그 연결이 어떤 종류의 작업을 할 수 있는지 정합니다. 이 장의 코드는 기존 페이지를 검색하고 읽으며(콘텐츠 읽기), 새 페이지를 만들고 거기에 블록을 붙입니다(콘텐츠 삽입). 연결을 만들 때 이 기능을 끄면 토큰이 맞아도 403 오류가 납니다.

③ 페이지 사용 권한이 노션의 독특한 점입니다. 토큰과 기능이 갖춰져도, 연결은 워크스페이스의 모든 문서를 볼 수 있는 게 아니라 사용자가 직접 골라 공유해 준 페이지만 볼 수 있습니다. 공유되지 않은 페이지를 요청하면 노션은 "권한이 없다"가 아니라 "그런 페이지는 찾을 수 없다"는 404로 답합니다. 연결 입장에서는 그 페이지가 없는 것과 같기 때문입니다. 그래서 404가 나면 페이지 ID가 틀렸을 가능성과 함께, 연결에 그 페이지를 공유했는지를 꼭 확인해야 합니다. 슬랙에서 봇을 채널에 초대해야 대화를 읽을 수 있었던 것과 같은 자리입니다.

페이지 사용 권한에는 편리한 성질이 하나 있습니다. 어떤 페이지를 연결에 공유하면 그 아래의 하위 페이지에도 같은 권한이 적용됩니다. 이 장에서는 에이전트 실습이라는 부모 페이지 하나만 공유하고, 저장 도구는 회의록을 이 페이지의 하위 페이지로 만듭니다. 그래서 회의록을 만들 때마다 권한을 따로 줄 필요가 없고, 방금 만든 회의록을 바로 다시 읽어 검증할 수도 있습니다. 회의록을 모을 부모 페이지를 따로 두는 것은 정리를 위해서이기도 하지만, 이렇게 연결이 손댈 수 있는 범위를 페이지 하나 아래로 좁히는 효과도 있습니다.

3.4이번 실습의 그래프 설계

LangGraph의 기본 재료는 2장에서 본 것과 같습니다. 노드들이 함께 읽고 쓰는 데이터 묶음인 상태(state), 상태를 받아 한 단계의 일을 하고 바뀐 칸만 돌려주는 함수인 노드(node), 한 노드 다음에 실행할 노드를 정하는 엣지(edge)입니다. 노드는 서로를 직접 부르지 않고, 데이터는 상태를 거쳐서만 오갑니다.

이번 장의 작업은 "메모를 회의록으로 정리한다"와 "회의록을 노션에 저장한다" 두 단계입니다. 2장처럼 노드 두 개를 엣지로 이어 그래프 하나로 만들 수도 있지만, 이 장의 코드는 노드 하나짜리 그래프를 두 개 만들고 그 사이에 사람이 확인하는 셀을 둡니다(그림 3.6).

맨 위의 NoteState에는 네 칸이 있습니다. memo와 title은 사람이 넣는 시작 입력이고, text는 작성 노드가, saved는 저장 노드가 채웁니다. 두 그래프는 이 상태 정의를 함께 쓰지만, 각자 필요한 칸만 다룹니다. draft_graph는 memo를 읽어 text를 돌려주고, save_graph는 title과 text를 읽어 saved를 돌려줍니다. 그림에서 칸의 색과 그 칸을 채우는 노드의 색을 맞춰 두었습니다.

그래프를 둘로 나눈 이유는 두 작업의 성질이 다르기 때문입니다. 작성은 모델을 한 번 더 부를 뿐이라 결과가 마음에 들지 않으면 몇 번이고 다시 실행해도 됩니다. 저장은 실행할 때마다 노션에 새 문서가 하나씩 생깁니다. 2장에서 "바깥에 흔적을 남기는 행동은 사람이 한 번 보고 실행한다"는 원칙으로 게시 셀을 그래프 밖에 뒀던 것과 같은 판단입니다. 이번에는 저장 자체도 그래프로 만들어 두었기 때문에, 저장 단계 역시 run_graph_logged()로 실행하며 [노드 완료] 같은 기록을 같은 형식으로 남길 수 있습니다. 대신 두 그래프 사이에 사람이 서 있습니다. 작성 결과를 읽고 고칠 곳이 있으면 고친 뒤, 그 값으로 저장 그래프를 실행합니다.

그래프에 들어가지 않는 도구도 있습니다. 서버의 세 도구 중 notion_search_pages와 notion_read_page는 그래프 안에서 쓰이지 않고, 실습 앞부분에서 연결을 확인할 때와 저장 뒤에 결과를 검증할 때 직접 부릅니다. 이번 장의 입력인 회의 메모는 노션에서 읽어 오는 것이 아니라 코드에 직접 적어 넣기 때문입니다.

확장 방향 · 2.4.3의 run_graph_logged()에는 그래프가 사람의 확인을 기다리며 멈출 때 나오는 __interrupt__를 처리하는 부분이 이미 들어 있습니다. LangGraph의 이 기능을 쓰면 draft → save를 그래프 하나로 잇고 그 사이에서 멈춰 승인을 받도록 바꿀 수 있습니다. 또 서버의 세 도구를 llm.bind_tools()로 모델에게 넘기면, "지난주 회의록을 찾아 읽고 이번 메모와 합쳐 새로 저장해 줘" 같은 요청을 모델이 도구를 골라 가며 처리하게 만들 수도 있습니다. 이 장에서는 각 단계를 눈으로 확인하기 위해 순서를 코드로 고정했습니다.

import os
import getpass

def read_secret(name: str) -> str:
    value = getpass.getpass(f"{name} 입력: ").strip()
    if not value or any(char.isspace() for char in value):
        raise ValueError(f"{name}을 공백과 줄바꿈 없이 다시 입력하세요.")
    os.environ[name] = value
    return value

getpass.getpass()는 입력한 값을 화면에 점으로 가려 받고, .strip()은 복사할 때 딸려 온 앞뒤 공백을 지웁니다. 값이 비었거나 중간에 공백이 있으면 잘못 복사한 경우가 대부분이라 바로 오류를 냅니다. 통과한 값은 os.environ[name]에 넣습니다. 이번 장에서는 이 함수를 OPENAI_API_KEY와 NOTION_TOKEN 두 번 부르며, 노션 토큰은 나중에 MCP 서버에 환경변수로 넘어가 노션 요청을 인증합니다.

execution_log는 모든 기록이 쌓이는 리스트이고, current_execution_log는 요청 하나의 기록만 따로 모을 때 쓰는 자리로 이 장에서는 비워 둡니다.

def log_step(stage, data):
    # 메시지 객체도 읽을 수 있는 JSON 값으로 바꿔 출력과 기록에 함께 사용합니다.
    def encode(value):
        return value.model_dump() if hasattr(value, "model_dump") else str(value)
    text = json.dumps(data, ensure_ascii=False, indent=2, default=encode)
    entry = {"stage": stage, "data": json.loads(text)}
    execution_log.append(entry)
    request_log = current_execution_log.get()
    if request_log is not None:
        request_log.append(entry)
    print(f"\n[{stage}]\n{text}", flush=True)

log_step("도구 호출", {"name": "notion_search_pages", "arguments": {"query": "에이전트 실습"}})를 실행하면 [도구 호출] 아래에 들여쓰기된 JSON이 찍힙니다. ensure_ascii=False는 한글이 코드로 깨지지 않게, indent=2는 줄을 나눠 읽기 좋게 합니다. 모델 메시지처럼 JSON으로 바로 바꿀 수 없는 객체는 안쪽의 encode()가 사전이나 문자열로 바꾸고, flush=True는 출력을 즉시 화면에 내보냅니다.

async def invoke_tool_logged(name, arguments):

    log_step("도구 결과", {"name": name, "result": result})
    return result

실행 전에 [도구 호출], 실행 후에 [도구 결과]를 남기고, 실패하면 [도구 실패]를 남긴 뒤 오류를 다시 던집니다. tool_map은 3.5.8에서 서버에 연결한 뒤에 만들어지지만, 이 함수는 정의만 해 두고 실제 호출은 그 뒤에 일어나므로 문제가 없습니다. 이번 장에서는 저장 도구가 실패했을 때 서버가 담아 보낸 "페이지는 생성됐지만 본문 저장 중 실패" 메시지가 이 [도구 실패] 기록에 그대로 나타납니다.

async def invoke_model_logged(model, messages):
    log_step("모델 입력", messages)
    try:
        response = await model.ainvoke(messages)
    except Exception as exc:
        log_step("모델 실패", {"error": f"{type(exc).__name__}: {exc}"})
        raise
    log_step("모델 응답", {"content": response.content, "tool_calls": response.tool_calls})
    return response

모델에 보낸 지시문과 메모를 [모델 입력]에, 받은 응답을 [모델 응답]에 남깁니다. 회의록에서 무언가 빠졌을 때 [모델 입력]에 그 내용이 있었는지부터 보면 원인이 메모 쪽인지 모델 쪽인지 바로 갈립니다.

async def run_graph_logged(graph, inputs, config=None):
    log_step("그래프 시작", inputs)
    final_state, interruptions = {}, ()
    try:
        async for mode, value in graph.astream(
            inputs, config=config, stream_mode=["updates", "values"],
        ):
            if mode == "values":
                final_state = value
            else:
                for node, output in value.items():
                    if node == "__interrupt__":
                        interruptions = output
                        log_step("사용자 확인 대기", output)
                    else:
                        log_step("노드 완료", {"node": node, "output": output})
    except Exception as exc:
        log_step("그래프 실패", {"error": f"{type(exc).__name__}: {exc}"})
        raise
    if interruptions:
        return {**final_state, "__interrupt__": interruptions}
    log_step("그래프 완료", final_state)
    return final_state

그래프를 graph.astream()으로 실행하면서, 노드가 끝날 때마다 넘어오는 updates(방금 끝난 노드가 돌려준 칸)는 [노드 완료]로 기록하고, values(그 칸까지 합쳐진 상태 전체)는 final_state에 덮어써 마지막 상태를 돌려줍니다. 이 대응 관계는 2장의 그림 2.24에서 자세히 보았습니다. 이번 장에서는 그래프가 두 개이므로 이 함수를 두 번 쓰게 됩니다.

3.5.6토큰·페이지 입력과 연결 확인

준비한 두 값을 노트북에 넣습니다. 토큰은 숨김 입력으로, 부모 페이지는 주소를 그대로 붙여 넣으면 코드가 페이지 ID를 꺼내 정리합니다.

입력창넣을 값복사한 곳
NOTION_TOKEN 입력:API 토큰연결 → classroom-agent → 구성 → API 토큰의 복사 버튼
Notion '에이전트 실습' 페이지 주소 또는 ID:부모 페이지 주소 전체에이전트 실습 문서를 연 브라우저 주소창
import re
import uuid
from urllib.parse import urlsplit, unquote

read_secret("NOTION_TOKEN");
page_input = input("Notion '에이전트 실습' 페이지 주소 또는 ID: ").strip()
path = unquote(urlsplit(page_input).path) if "://" in page_input else page_input
last_part = path.rstrip("/").split("/")[-1]
match = re.search(r"([0-9a-fA-F]{32}|[0-9a-fA-F]{8}(?:-[0-9a-fA-F]{4}){3}-[0-9a-fA-F]{12})$", last_part)
if not match:
    raise ValueError("페이지의 전체 링크 또는 32자리 페이지 ID를 입력하세요.")
os.environ["NOTION_PARENT_PAGE_ID"] = str(uuid.UUID(match.group(1)))
print("부모 페이지 ID:", os.environ["NOTION_PARENT_PAGE_ID"])

토큰은 read_secret()이 NOTION_TOKEN에 넣습니다. 나머지 코드는 사람이 붙여 넣는 값이 여러 모양일 수 있다는 점을 처리합니다. 노션 페이지를 가리키는 값은 주소 전체일 수도, 32자리 ID만일 수도, 3f8f34db-cc48-…처럼 하이픈이 들어간 ID일 수도 있습니다. 실행 결과를 보면 이번에는 하이픈이 들어간 ID를 붙여 넣었습니다.

  • 주소에서 경로만 꺼내기 · 입력에 ://가 있으면 주소로 보고 urlsplit()으로 나눈 뒤 경로 부분만 씁니다. ?showMoveTo=true… 같은 뒷부분이 여기서 떨어져 나갑니다. unquote()는 주소 안의 %20 같은 표기를 원래 문자로 되돌립니다.
  • 마지막 조각만 보기 · 경로를 /로 나눠 마지막 조각을 고릅니다. 노션 주소는 /p/ID일 수도 있고 /워크스페이스/페이지-제목-ID처럼 제목이 앞에 붙을 수도 있는데, 어느 쪽이든 ID는 끝에 있습니다.
  • ID 모양 찾기 · 정규식은 끝에 붙은 32자리 16진수, 또는 8-4-4-4-12 자리로 하이픈이 들어간 형태를 찾습니다. 둘 다 아니면 다시 입력하라는 오류를 냅니다.
  • 모양을 하나로 맞추기 · uuid.UUID()를 거쳐 문자열로 바꾸면 어떤 형태로 들어왔든 하이픈이 들어간 소문자 형태 하나로 정리됩니다. 노션 API가 돌려주는 페이지 ID도 이 형태라서, 3.5.10에서 저장된 문서의 부모 ID와 이 값을 문자열로 바로 비교할 수 있습니다.

정리한 ID는 NOTION_PARENT_PAGE_ID에 넣습니다. 저장 도구는 이 값을 읽어 그 페이지 아래에 회의록을 만듭니다. 이제 이 두 값으로 노션 API를 직접 불러, 토큰과 페이지 권한이 정말 갖춰졌는지 확인합니다.

import httpx

headers = {"Authorization": "Bearer " + os.environ["NOTION_TOKEN"],
           "Notion-Version": "2025-09-03"}
async with httpx.AsyncClient(timeout=None) as http:
    response = await http.get(
        "https://api.notion.com/v1/pages/" + os.environ["NOTION_PARENT_PAGE_ID"],
        headers=headers,
    )
if response.status_code != 200:
    error = response.json()
    raise RuntimeError(f"Notion 페이지 확인 실패: HTTP {response.status_code}, "
                       f"{error.get('code', 'unknown')}: {error.get('message', '')}")
parent_page = response.json()
parent_title = "".join(
    item.get("plain_text", item.get("text", {}).get("content", ""))
    for prop in parent_page.get("properties", {}).values() if prop.get("type") == "title"
    for item in prop.get("title", [])
)
print("부모 페이지 접근 성공:", parent_page["url"])
print("부모 페이지 제목:", parent_title)

노션 API는 요청 머리말에 두 가지를 요구합니다. Authorization: Bearer 토큰은 그림 3.5의 ① 겹을 통과하기 위한 것이고, Notion-Version은 이 요청을 어느 날짜 판의 API 규칙으로 처리할지 알려 줍니다. 노션은 API의 요청·응답 모양을 바꿀 때 새 버전 날짜를 붙여 내놓으므로, 버전을 적어 두면 나중에 노션이 API를 바꿔도 이 코드가 기대하는 모양의 응답을 계속 받을 수 있습니다. 라이브러리 버전을 숫자로 못 박아 둔 것과 같은 이유입니다.

요청은 GET /v1/pages/{부모 ID}, 즉 그림 3.3 왼쪽의 페이지 객체를 받는 요청입니다. 노션은 실패하면 상태 코드 자체가 200이 아니므로, 상태 코드를 보고 실패면 응답 본문의 code와 message를 꺼내 오류를 냅니다. 여기서 401이 나오면 토큰을, 404가 나오면 페이지 ID와 3.5.5의 페이지 사용 권한을 확인합니다.

성공하면 페이지 객체에서 제목을 꺼냅니다. 3.2.1에서 본 대로 제목은 본문이 아니라 properties 안의 type이 title인 속성에 들어 있고, 그 값은 rich_text 조각의 배열입니다. 코드의 이중 반복문이 하는 일이 바로 이것입니다. 모든 속성 중 제목 속성을 고르고, 그 안의 조각마다 plain_text를 꺼내 이어 붙입니다. plain_text가 없는 조각에 대비해 text.content를 대신 읽게 해 두었습니다. 출력에 주소와 에이전트 실습이라는 제목이 나오면 세 겹을 모두 통과한 것입니다.

이 셀에서 만든 headers 변수는 3.5.10의 검증 셀에서 다시 씁니다. 중간에 세션을 재시작했다면 이 셀을 다시 실행해 두어야 합니다.

%%writefile -a notion_mcp.py
async def notion_api(method: str, path: str, payload: dict | None = None) -> dict:
    headers = {
        "Authorization": "Bearer " + os.environ["NOTION_TOKEN"],
        "Notion-Version": "2025-09-03",
    }
    async with httpx.AsyncClient(timeout=None) as client:
        response = await client.request(
            method, "https://api.notion.com/v1/" + path,
            headers=headers, json=payload,
        )
    if response.status_code >= 400:
        try:
            data = response.json()
        except ValueError:
            data = {"message": response.text}
        detail = data.get("message", "")
        retry_after = response.headers.get("Retry-After")
        raise RuntimeError(
            f"Notion {method} {path} 실패: HTTP {response.status_code}, "
            f"{data.get('code', 'unknown')}: {detail} "
            f"(Retry-After={retry_after})"
        )
    return response.json()

@mcp.tool()
async def notion_search_pages(query: str) -> str:
    """공유된 Notion 페이지를 제목으로 검색하고 모든 결과 페이지를 읽습니다."""
    payload = {"query": query, "filter": {"value": "page", "property": "object"}}
    pages = []
    while True:
        data = await notion_api("POST", "search", payload)
        pages.extend({"id": page["id"], "title": page_title(page), "url": page["url"]}
                     for page in data.get("results", []))
        if not data.get("has_more"):
            break
        payload["start_cursor"] = data["next_cursor"]
    return json.dumps({"pages": pages, "count": len(pages)}, ensure_ascii=False)

notion_read_page: 읽기 도구

%%writefile -a notion_mcp.py
@mcp.tool()
async def notion_read_page(page_id: str) -> str:
    """Notion 페이지의 모든 블록 페이지와 하위 블록을 읽습니다."""
    page_id = str(uuid.UUID(page_id))
    pending = [("fetch", page_id, None, 0)]
    blocks, text_parts = [], []
    while pending:
        action, value, cursor, depth = pending.pop()
        if action == "fetch":
            path = f"blocks/{value}/children"
            if cursor:
                path += "?" + urlencode({"start_cursor": cursor})
            data = await notion_api("GET", path)
            if data.get("has_more"):
                pending.append(("fetch", value, data["next_cursor"], depth))
            for block in reversed(data.get("results", [])):
                pending.append(("block", block, None, depth))
            continue
        block = value
        blocks.append({"depth": depth, "block": block})
        content = block.get(block["type"], {})
        if block["type"] == "table_row":
            text = " | ".join("".join(item.get("plain_text", item.get("text", {}).get("content", ""))
                                       for item in cell) for cell in content.get("cells", []))
        else:
            text = "".join(item.get("plain_text", item.get("text", {}).get("content", ""))
                           for item in content.get("rich_text", []))
        if text:
            text_parts.append(text)
        if block.get("has_children"):
            pending.append(("fetch", block["id"], None, depth + 1))
    return json.dumps({"page_id": page_id, "text": "\n".join(text_parts),
                       "blocks": blocks, "block_count": len(blocks)}, ensure_ascii=False)

Appending to notion_mcp.py

3.2.2에서 말한 "쪽 넘기기와 나무 따라가기가 겹치는" 일을 하는 도구로, 이 장에서 가장 읽기 까다로운 코드입니다. 첫 줄의 str(uuid.UUID(page_id))는 3.5.6에서처럼 어떤 모양으로 들어온 ID든 하이픈이 들어간 표준 형태로 맞춥니다. 모양이 틀린 값이면 여기서 바로 오류가 나서, 노션에 엉뚱한 요청을 보내기 전에 걸러집니다.

이어지는 반복문의 핵심은 pending이라는 목록입니다. 이 목록에는 "앞으로 할 일"이 쌓이고, pending.pop()은 맨 뒤(가장 최근에 쌓은 것)부터 하나씩 꺼냅니다. 할 일은 두 종류입니다.

  • ("fetch", ID, cursor, depth) · 그 ID의 자식 블록을 노션에 요청하라는 일입니다. 받아 온 블록들을 하나하나 ("block", …) 일로 바꿔 다시 쌓습니다.
  • ("block", 블록, None, depth) · 그 블록에서 글을 꺼내 기록하라는 일입니다. 블록에 하위 블록이 있으면(has_children) 그 블록 ID로 새 fetch 일을 쌓습니다.

말로는 헷갈리니 작은 예로 따라가 보겠습니다. 페이지 P에 문단 A, 토글 B(안에 문단 B1), 문단 C가 차례로 있다고 합시다(그림 3.17).

2단계에서 P의 자식 A, B, C를 받으면 코드는 reversed()로 거꾸로 쌓습니다. pop()이 맨 뒤부터 꺼내므로, C·B·A 순으로 쌓아야 A부터 꺼내지기 때문입니다. 4단계에서 B를 꺼내면 B의 글 "토글"을 기록하고, B에 하위 블록이 있으니 fetch B를 쌓습니다. 이 일은 아직 남은 C보다 위에 쌓이므로 C보다 먼저 처리되고, 그 결과 B1의 "나"가 "토글"과 "다" 사이에 들어갑니다. 결과적으로 글은 화면에서 위에서 아래로 읽는 순서 그대로 모입니다. 블록 안에 블록이 몇 겹으로 들어 있든 같은 규칙으로 끝까지 내려갑니다.

쪽 넘기기도 같은 목록으로 처리합니다. 자식 블록이 많아 응답에 has_more가 오면, 코드는 받은 블록들을 쌓기 전에 다음 쪽을 받을 일(("fetch", 같은 ID, next_cursor, depth))을 먼저 쌓습니다. 그러면 그 일은 이번 쪽 블록들 아래에 깔려서, 이번 쪽 블록을 (그 하위 블록까지) 모두 처리한 뒤에야 꺼내집니다. 다음 쪽의 블록이 이번 쪽보다 앞에 끼어드는 일이 없습니다.

같은 일을 "자기 자신을 다시 부르는 함수"(재귀)로 짤 수도 있지만, 할 일 목록을 직접 관리하면 아주 깊이 중첩된 문서에서도 파이썬의 재귀 깊이 제한에 걸리지 않고, 쪽 넘기기와 하위 블록 탐색을 한 반복문 안에서 다룰 수 있습니다.

글을 꺼내는 부분도 3.2.1의 구조를 그대로 따릅니다. block[block["type"]]은 블록 종류와 같은 이름의 칸, 예를 들어 문단이면 block["paragraph"]를 꺼냅니다. 대부분의 블록은 그 안의 rich_text 조각을 이어 붙이면 되지만, 표의 행(table_row)은 글이 cells에 칸별로 들어 있으므로 칸마다 조각을 이어 붙인 뒤 " | "로 연결합니다. depth는 그 블록이 몇 겹 안쪽에 있는지를 기록하는 값으로, 페이지 바로 아래 블록은 0, 그 하위 블록은 1입니다.

반환값에는 이어 붙인 글(text, 블록마다 줄을 바꿈), 원래 블록 정보(blocks), 읽은 블록 수(block_count)가 들어갑니다. 글만 돌려주지 않고 원래 블록까지 함께 돌려주는 것은 3.5.10의 검증 때문입니다. 그 이유는 거기서 보겠습니다.

%%writefile -a notion_mcp.py
@mcp.tool()
async def notion_create_note(title: str, text: str) -> str:
    """설정된 부모 페이지 아래에 새 문서를 만들고 본문 전체를 저장합니다."""
    parent_id = str(uuid.UUID(os.environ["NOTION_PARENT_PAGE_ID"]))
    # Notion rich_text 한 항목의 실제 API 한도: 2,000자.
    title_items = [{"type": "text", "text": {"content": title[i:i + 2000]}}
                   for i in range(0, len(title), 2000)]
    page = await notion_api("POST", "pages", {
        "parent": {"page_id": parent_id},
        "properties": {"title": {"type": "title", "title": title_items}},
    })
    batch = []
    saved_characters = 0
    try:
        for i in range(0, len(text), 2000):
            block = {"object": "block", "type": "paragraph", "paragraph": {
                "rich_text": [{"type": "text", "text": {"content": text[i:i + 2000]}}]
            }}
            candidate = {"children": batch + [block]}
            size = len(json.dumps(candidate, ensure_ascii=False, separators=(",", ":")).encode("utf-8"))
            # API 한 요청의 배열 100개와 본문 500KB 한도에 맞춰 나눠 전송합니다.
            if batch and (len(batch) == 100 or size > 500_000):
                await notion_api("PATCH", f"blocks/{page['id']}/children", {"children": batch})
                saved_characters += sum(len(b["paragraph"]["rich_text"][0]["text"]["content"]) for b in batch)
                batch = []
            batch.append(block)
        if batch:
            await notion_api("PATCH", f"blocks/{page['id']}/children", {"children": batch})
            saved_characters += sum(len(b["paragraph"]["rich_text"][0]["text"]["content"]) for b in batch)
    except Exception as exc:
        raise RuntimeError(
            f"페이지는 생성됐지만 본문 저장 중 실패했습니다. url={page['url']}, "
            f"저장 확인된 문자 수={saved_characters}, 원인={type(exc).__name__}: {exc}"
        ) from exc
    return json.dumps({"id": page["id"], "url": page["url"], "created": True,
                       "saved_characters": saved_characters}, ensure_ascii=False)

② 본문 나눠 붙이기. 본문은 2,000자씩 잘라 조각 하나를 담은 문단 블록으로 만들고, 블록을 batch에 모았다가 한 번에 붙입니다. 블록을 하나 더하기 전에, 그 블록을 더한 요청 본문(candidate)을 실제로 보낼 모양 그대로 JSON으로 만들어 UTF-8 바이트 크기를 잽니다. separators=(",", ":")는 JSON에서 공백을 빼고 가장 짧게 만드는 옵션으로, httpx가 실제로 보낼 때의 크기에 가깝게 재기 위한 것입니다. 이미 100개가 모였거나 이 블록을 더하면 500KB를 넘게 되면, 지금까지 모은 블록을 먼저 PATCH로 보내고 batch를 비운 뒤 새 블록을 넣습니다. 반복이 끝나면 남은 블록을 마지막으로 보냅니다. 입력 길이에 따라 이 과정이 어떻게 달라지는지는 그림 3.18과 같습니다.

저장 글자 수 세기와 실패 처리. 블록 묶음 하나를 보내는 데 성공할 때마다 그 묶음에 든 글자 수를 saved_characters에 더합니다. 본문 붙이기 중 어느 요청이든 실패하면 except로 잡아, 이미 만들어진 페이지의 주소와 그때까지 저장이 확인된 글자 수를 담은 새 오류를 냅니다. 3.2.2에서 말한 "무엇이 어디까지 저장됐는지 정확히 알려 주기"가 이 부분입니다. raise … from exc는 원래 오류를 새 오류에 연결해 두는 문법으로, 기록에서 노션이 보낸 원래 오류 내용도 함께 볼 수 있게 합니다. ① 페이지 생성 자체가 실패한 경우는 이 try 밖이라 notion_api()의 오류가 그대로 올라오는데, 그때는 만들어진 페이지가 없으니 따로 알려 줄 것도 없습니다.

모든 블록을 보내면 새 페이지의 id, url, 그리고 saved_characters를 돌려줍니다. 요청한 본문 길이와 이 값이 같으면 잘린 부분 없이 모두 보낸 것입니다. 다만 이것은 "노션이 요청을 받아들였다"는 뜻이지 "저장된 내용이 보낸 것과 같다"는 확인은 아니므로, 3.5.10에서 따로 다시 읽어 비교합니다.

def tool_json(value):
    # MCP 도구가 돌려준 JSON 문자열을 파이썬 dict로 바꿉니다.
    if isinstance(value, str):
        return json.loads(value)
    if isinstance(value, list):

                         if isinstance(item, dict) and item.get("type") == "text")

제목과 위치는 노션 API를 직접 부릅니다. 읽기 도구는 블록만 읽고 페이지 객체의 제목이나 부모 위치는 돌려주지 않기 때문입니다. 요청 머리말은 3.5.6에서 만들어 둔 headers를 그대로 쓰고, 제목은 3.5.6과 같은 이중 반복문으로 꺼냅니다. 부모 위치는 응답의 parent.page_id를 환경변수의 부모 ID와 비교합니다. 두 값 모두 하이픈이 들어간 형태라 문자열로 바로 비교할 수 있는데, 3.5.6에서 입력을 uuid.UUID()로 정리해 둔 덕분입니다. 입력을 하이픈 없는 32자리 그대로 저장했다면 같은 페이지인데도 비교 결과가 False로 나왔을 것입니다.

본문은 읽기 도구의 text가 아니라 blocks에서 다시 조립합니다. 여기에 이 장의 코드에서 가장 섬세한 판단이 들어 있습니다. 읽기 도구의 text는 블록마다 줄을 바꿔 이어 붙인 값입니다. 그런데 생성 도구는 본문을 줄 단위가 아니라 2,000자 단위로 기계적으로 잘라 블록에 나눠 담았습니다. 본문이 2,000자를 넘어 블록 두 개로 나뉘었다면, text에는 원래 없던 줄바꿈이 그 경계에 하나 끼어들어 원문과 달라집니다. 그래서 검증 코드는 페이지 바로 아래(depth == 0)의 문단 블록에서 rich_text 조각을 꺼내 아무것도 끼우지 않고 이어 붙입니다. 잘랐던 조각을 자른 그대로 다시 붙이는 것이라, 블록이 몇 개로 나뉘었든 원문과 정확히 같아야 합니다. 읽기 도구가 글만이 아니라 원래 블록 정보까지 돌려주게 만든 이유가 이것입니다.

검증에도 MCP 도구(읽기 도구)를 함께 쓴 점은 2장과 다릅니다. 2장에서는 확인하는 쪽까지 같은 도구를 쓰면 도구의 문제를 그대로 안고 갈 수 있다며 검증을 슬랙 API 직접 호출로만 했습니다. 이번에는 본문을 읽으려면 3.5.7의 나무 따라가기를 노트북에 다시 짜야 하므로 읽기 도구를 썼고, 대신 제목과 위치는 도구를 거치지 않는 직접 호출로 확인해 한쪽에 치우치지 않게 했습니다. 읽기 도구는 생성 도구와 다른 API(GET blocks)를 쓰는 별개의 코드이므로, 생성 도구의 실수를 그대로 되풀이할 가능성도 낮습니다.

실습 중 오류가 나면 멈춘 단계의 마지막 기록부터 봅니다. 모델 쪽 문제는 [모델 입력]과 [모델 실패]에, 노션 쪽 문제는 [도구 호출]과 [도구 실패]에 원인이 남아 있습니다. 노션 오류는 그림 3.5의 세 겹 중 어디에서 막혔는지를 먼저 생각하면 빨리 풀립니다.

이 장에서는 회의 메모를 회의록으로 정리해 노션에 저장하는 봇을 만들었습니다. 노션 API를 다루는 코드는 모두 MCP 서버(notion_mcp.py)에 두었고, 노트북은 2장과 똑같은 클라이언트 코드로 서버 설정만 바꿔 도구 세 개를 불러 썼습니다. 작성과 저장은 노드 하나짜리 그래프 두 개로 나누고 그 사이에 사람이 확인하는 셀을 두었으며, 저장한 뒤에는 문서를 다시 읽어 제목·본문·위치가 보낸 값과 같은지 검증했습니다.

2장과 비교하면 이번 장의 새로운 내용은 거의 모두 서버 안쪽에 있었습니다. 페이지와 블록으로 나뉜 노션의 구조 때문에 읽기 도구는 하위 블록을 따라 내려가야 했고, 생성 도구는 요청 두 번과 세 가지 한도를 다뤄야 했으며, 그 사이에서 실패했을 때 무엇이 남았는지 알려 줘야 했습니다. 그런데 노트북의 그래프 노드는 그중 아무것도 몰랐습니다. 도구 이름과 인자만 넘겼을 뿐입니다. 서비스마다 다른 복잡함을 서버 안에 가두고 바깥에는 단순한 도구 이름만 내놓는 것, 그것이 MCP 서버를 따로 두는 이유이고 이번 장에서 직접 확인한 점입니다. 이렇게 만든 notion_mcp.py는 노트북이 아닌 다른 MCP 클라이언트에서도 그대로 쓸 수 있고, 2장의 슬랙 서버와 함께 연결하면 "슬랙 대화를 요약해 노션에 회의록으로 남기는" 일도 같은 틀 안에서 이어 붙일 수 있습니다.
